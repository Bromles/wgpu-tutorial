# План полной переработки руководства

## Контекст и цель

- Аналог LearnOpenGL для **Rust + native wgpu**, без браузера/WASM.
- Аудитория: опытные Rust-разработчики без знаний компьютерной графики. Rust не объясняем; графику и необходимую математику объясняем внутри курса.
- Нужна полная переработка учебного маршрута, подачи и сцен, а не только исправление формулировок или перестановка текущих глав.
- Учим возможностям и техникам графики, а не воспроизводим рендер конкретной игры. Реальные реализации служат мотивацией, но не определяют обязательные сцены, форматы данных или архитектуру курса.
- Этот файл является единым актуальным планом переработки.
- Детализация этапа 1: [карта знаний](KNOWLEDGE_MAP.md) задаёт порядок объяснения/применения понятий и зависимости глав. Этот файл хранит общие решения, карта — конкретный учебный маршрут.
- Детализация этапа 2: [индекс паспортов](CHAPTER_PASSPORTS.md) и тематические файлы в `planning/` задают сцены, границы страниц и будущие проверки. Для работы с главой читать её паспорт, не все документы целиком.

## Учебные принципы

1. Ничего существенного не появляется из воздуха: объяснение понятия предшествует его использованию. Внешние ссылки необязательны для прохождения.
2. Структура урока: **наблюдаем проблему → строим модель → выражаем через wgpu → проверяем результат → обсуждаем ограничения**.
3. Для новой величины указывать смысл, пространство координат, единицы; для ресурса: кто читает/пишет и когда.
4. Математика вводится рядом с задачей. Например, барицентрические координаты: смешивание на отрезке → три веса → геометрия площадей → формула → название → интерполяция GPU. Не использовать термин вместо объяснения.
5. Различать общий принцип графики, соглашение курса, требование API и упрощение демо. Объяснённая абстракция допустима; скрытая необходимая концепция нет.
6. Внутри эксперимента менять один изучаемый фактор. Текст, код, схема, эталонный кадр и упражнение должны описывать один эксперимент.
7. Справочник собирает уже введённые правила; обязательное объяснение нельзя выносить только туда.
8. Сразу учим корректной модели, постепенно усложняя задачи. Не строим заведомо неудобную реализацию ради последующего «правильного» решения. Альтернативы вводим до задач, где они уместнее.
9. Один учебный вопрос → один проверяемый эксперимент, не обязательно новая картинка: результатом могут быть одинаковое изображение при разных путях данных, проверенный layout или измеренная стоимость. Подход LearnOpenGL заимствуем без его исторических ограничений API.

## Целевая структура

Три слоя: последовательный основной маршрут, ответвления с явными prerequisites и вводимые по мере надобности английские термины в тексте глав. На главной: карта, проверенная готовая часть и отдельно roadmap.

| Часть                         | Последовательность тем                                                                                                                                                                                                                                                                                    |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| I. Как появляется изображение | Пиксель/RGB/координаты изображения → CPU/GPU/команды → окно и очистка → первый треугольник и стадии растеризации → извлечение оконного фреймворка                                                                                                                                                            |
| II. Данные и изображение      | Интерполяция → Buffer/usages и vertex/index fetch → layout/bindings/uniforms → обновление данных и время исполнения → read-only storage и vertex pulling → immediates → linear RGB/sRGB → текстуры/UV/sampling → minification/mipmaps                                                                     |
| III. Пространство и видимость | Преобразования на плоскости → матрицы/композиция/однородные координаты → local/world, нормализация/dot/cross и базис → обратное преобразование/камера/проекция → clip/отсечение/perspective divide/NDC/viewport и перспективная интерполяция → winding/culling/depth → управляемая native-камера → UV-швы |
| IV. Поверхность и свет        | Нормали и применение известных векторных операций → один источник и Lambert → normal matrix → материал/specular/Blinn–Phong → point/spot/attenuation/несколько источников → alpha/blending/порядок/depth writes → mesh/material/object и несколько draw без движка                                                                                           |
| V. Как устроен кадр           | базовый compute и визуализация результата → RTT и граф зависимостей render/compute операций → shadow mapping → MSAA/resolve → HDR/exposure/tone mapping/SDR output → законченная небольшая сцена                                                                   |

Ответвления:

- Масштабирование: instancing, per-object data, компактные представления данных, indirect drawing.
- Поверхности: TBN/normal mapping после UV, нормалей и материалов.
- Окружение и затенение: кубические карты и skybox после depth; тени точечного источника после shadow mapping; ambient occlusion после промежуточных текстур.
- Продвинутый compute: workgroup memory/barriers/atomics, чтение соседей/ping-pong, reductions/compaction/GPU culling. Затем bloom (также требует HDR), particles (также требует blending).
- Архитектура: от явного многопроходного кадра к локальной реализации небольшого render graph; не внедрять его в общий фреймворк.
- Модели/PBR: загрузка сцены, metallic-roughness, environment maps, IBL.
- Продвинутое освещение: базовый deferred/G-buffer, сравнение и forward-прозрачность; CPU tiled → GPU tiled → clustered на общих списках для обоих shading-путей. Разделять организацию shading и отбор источников; обсуждать bandwidth, overdraw, материалы, прозрачность и MSAA. Реализация deferred MSAA вне базового сравнения; PBR и render graph не prerequisites.
- Native-практика: capabilities/limits, GPU capture, timestamps, конкретные расширения с проверкой поддержки. Не все полезные native-инструменты являются native-only features.

Ключевые зависимости: **instancing не нужен для первого света; RTT предшествует теням; несколько мешей не разрывают постпроцессинг; PBR не заменяет объяснение базовых материалов**. Точные границы глав уточняются по карте знаний.

## Данные и исполнение

- Различать ресурс (`Buffer`), способ доступа (vertex fetch/uniform/storage) и стадию-потребителя (vertex/fragment/compute). Storage не привязан к compute; vertex fetch не является устаревшим или неправильным подходом.
- Рано сравнить vertex fetch и vertex pulling на одинаковой геометрии, сначала без изменения её представления. Объяснить адресацию, layout, преобразование форматов, limits; не обещать универсального выигрыша storage.
- Затем показать, как явная адресация и восстановление данных в шейдере позволяют убрать дублирование и сократить объём хранения/загрузки. Выбор storage сам по себе данные не сжимает; представление и способ доступа — отдельные решения. Учебную сцену выбирать под этот принцип, не под формат конкретной игры.
- Immediates: небольшие параметры, задаваемые при записи команд, без отдельного пользовательского buffer binding. В wgpu 30: `Features::IMMEDIATES`, `set_immediates`, `PipelineLayoutDescriptor::immediate_size`, `Limits::max_immediate_size`, WGSL `var<immediate>` ([API](https://docs.rs/wgpu/30.0.0/wgpu/struct.Features.html#associatedconstant.IMMEDIATES)). Механизм уже есть в WebGPU/WGSL; не маркировать автоматически native-only по прежнему названию push constants.
- Показать совместное применение: uniform с камерой + storage с таблицей объектов + immediate с индексом текущего объекта. Объяснять feature/limit requirements до использования; не запрашивать все features без разбора.
- Базовый compute обязателен в основном маршруте после bindings/storage и до сложных эффектов: invocation/workgroup/dispatch, округление размера запуска, bounds check, независимые записи и последующее чтение render pass. Новое здесь — исполнение и запись, а не существование storage.
- Обработку изображения можно выразить fullscreen draw с fragment shader или compute dispatch. На подходящей задаче сравнить адресацию, sampling, запись результатов, workgroup-возможности и измеренную стоимость. Fragment-путь не считать заведомо неправильной «эмуляцией», compute не обещать как автоматическое ускорение; выбирать механизм по задаче.
- Со второго прохода рисовать граф: операции, читаемые/записываемые ресурсы, зависимости, lifetime, formats/usages. Сначала явный код, затем при доказанной потребности автоматизация. Render graph не гарантирует ускорения, параллелизма или отдельной async compute queue; отделять его задачи от синхронизации, выполняемой wgpu.

## Код и оконный фреймворк

- После первого треугольника отдельным учебным шагом извлечь **только уже объяснённый код** окна, базовой инициализации wgpu, acquire/present, resize и жизненного цикла.
- Затем заморозить функциональный объём общего фреймворка. Исправления ошибок допустимы; наращивание будущими учебными механизмами нет.
- В ней не должно быть камеры, input controller, генераторов геометрии, загрузчиков текстур, материалов, света, сцены, ECS или renderer abstraction.
- Поздние архитектурные главы могут вводить локальные абстракции, включая render graph, после объяснения автоматизируемого явного кода. Заморожен общий фреймворк, а не развитие знаний читателя.
- Не проектировать её API заранее под PBR/compute. Новые требования к device/features позднее раскрывать явно, не менять незаметно ранний bootstrap.
- **Каждая глава имеет законченный запускаемый снимок проекта**, содержащий только введённые к этому моменту модули.
- Камера и другие повторяемые учебные модули локальны для снимков. Осознанное дублирование лучше общей библиотеки с будущими концепциями.
- В статье не повторять весь проект: показывать новые/изменённые фрагменты, карту файлов и перечень перенесённого без изменений. По возможности включать фрагменты из исходников.
- Читатель может продолжать свой проект или запускать готовый снимок. Git diff не должен быть обязательным способом понять урок.
- В начале главы: откуда продолжаем, что сохраняем, что меняем, что должно измениться на экране. Читатель во время чтения запускает снимок предыдущей главы, поэтому команда запуска нового снимка живёт в разделе «Снимок» вместе с его проверкой.
- Конвенции кода: понятные описательные имена, диагностические labels ресурсов, явное соответствие vertex attributes и входов WGSL, содержательные сообщения ошибок.

## Сцены и визуальные материалы

Сначала проектировать эксперимент, затем писать код и статью. Паспорт сцены: цель, понятное исходное состояние, изменяемая величина, ожидаемый эффект, мешающие факторы, диагностические режимы.

| Стенд                                  | Назначение                                                              |
| -------------------------------------- | ----------------------------------------------------------------------- |
| Один треугольник                       | Покрытие, атрибуты, численно проверяемая интерполяция                   |
| Размеченный прямоугольник              | UV, sampling, преобразования; асимметричная текстура с подписями        |
| Два пересекающихся объекта             | Depth и порядок рисования                                               |
| Объект с осями и полом                 | Камера и проекция                                                       |
| Наклонная поверхность / гладкий объект | Нормали, normal matrix, материалы; осевой куб не показывает все эффекты |
| Объект над плоскостью                  | Caster/receiver, shadow map, bias                                       |
| Контрастная сцена с ярким источником   | MSAA, HDR, bloom                                                        |

- Не одна сетка кубов на весь курс и не новая сложная сцена в каждой главе. Стабильные стенды внутри тем.
- Нужны **схема модели + эталон результата + диагностическое сравнение**. Например, тени: light frustum, shadow map, visibility mask, acne/bias/Peter Panning; bloom: все промежуточные изображения.
- Фиксированные исходные камера/свет/seed; сброс, пауза, on/off изучаемого эффекта там, где полезно.
- Входной меш можно использовать как явно обозначенные данные понятного формата. Если даём его генератор как учебный код, объясняем и генератор, не прячем в helper.
- Для сайта достаточно изображений и коротких видео; браузерный рендер не нужен.

### Сравнение техник

- Для альтернативных представлений и способов исполнения сохранять сопоставимые входные данные и результат; изменения batching, точности и алгоритма учитывать отдельно.
- Измерять объём хранения/загрузки, CPU preparation/submission и GPU time. Фиксировать backend/GPU, разрешение, прогрев и влияние VSync. Сокращение числа записей не означает такое же сокращение байтов, shader invocations или времени кадра.
- Конкретные стенды для этих сравнений выбрать при составлении паспортов глав. Компактная геометрия и обработка изображений — возможные задачи, а не обязательное повторение чьего-либо рендерера.

## Готовность и риски

Глава готова, когда понятия введены вовремя, код соответствует тексту, результат воспроизводится, упражнения дают обещанный эффект и важная логика не скрыта в общих модулях. Одной компиляции недостаточно.

Проверки: сборка сайта и Rust на PR и push (`.github/workflows/ci.yml`); численные проверки layout/проекции/winding; WGSL/pipeline validation; GPU smoke-прогоны; эталонные кадры без требования побитового совпадения разных GPU. Эталонные кадры и численная проверка содержимого — offscreen-рендер с readback в отдельном верификационном крейте (подход wgpu-test: сравнение с эталонными PNG, используемыми и в статьях), заводится с главы 04; readback не появляется в учебном коде снимков раньше B1. Захват presented-пикселей окна не используем: событийный lifecycle поверхности достаётся интерактивным чек-листам статей.

В предыдущем ревью обнаружены основания не переносить старые объяснения без проверки:

- `code/framework/src/gpu.rs`: configure при живом `Suboptimal(frame)` нарушает lifecycle; `input.rs` теряет mouse delta из-за перезаписи.
- Неверные обобщения про CPU/GPU submit, uniform size/alignment, clip/NDC, интерполяцию и sampling в compute; часть повторяется в глоссарии.
- Текст shadows описывает bias, код использует другой подход; bloom путает texel offsets и UV.
