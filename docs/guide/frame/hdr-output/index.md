# HDR и вывод

::: info Только native
Снимок [главы «Материал и блик»](../../space-light/blinn-phong/): та же плоскость, камера и формула Blinn–Phong, перенесённые в промежуточный кадр [«Промежуточный кадр»](../render-to-texture/). Клавиши: `[`/`]` — экспозиция, `I` — интенсивность света, `D` — диагностика clipping.
:::

Блик в центре плоскости при интенсивности 0.6 — linear 0.77: влезает в байт.
Поднимите интенсивность до 4.0 — и центр станет linear 4.85.
Куда записать 4.85 в текстуру, которая останавливается на 1.0? Обычный ответ — clamp, и весь диапазон от 1.0 до бесконечности схлопывается в одну белую заплатку: **информации больше нет**.

HDR-рендеринг (high dynamic range — расширенный динамический диапазон) разделяет вопрос на два: *как хранить* свет любой яркости и *как показать* его на экране с диапазоном [0, 1].

## Промежуточный кадр — float

Цепочка из [«Промежуточный кадр»](../render-to-texture/) меняет одну строчку — формат:

```rust
        let texture = gpu.device.create_texture(&TextureDescriptor {
            label: Some("HDR frame"),
            size: Extent3d {
                width,
                height,
                depth_or_array_layers: 1,
            },
            mip_level_count: 1,
            sample_count: 1,
            dimension: TextureDimension::D2,
            // Linear half-float HDR: 0.35 and 4.85 are equally valid
            // stored values; there is no sRGB variant of a float format.
            format: TextureFormat::Rgba16Float,
            usage: TextureUsages::RENDER_ATTACHMENT | TextureUsages::TEXTURE_BINDING,
            view_formats: &[],
        });
```

`Rgba16Float` — половинная точность с плавающей точкой: значения не привязаны к [0, 1], 0.05 тени и 4.85 блика хранятся одинаково спокойно.
Формат **линейный**: у float-текстур sRGB-варианта не существует — кодированием он не занимается.
Шейдер сцены всё тот же Blinn–Phong — меняется только то, что его ответ больше никто не обрезает:

```wgsl
    let color = params.material.albedo * (AMBIENT + params.light.intensity * diffuse)
        + params.material.specular * (params.light.intensity * spec_factor);
    // Linear HDR output: the float target stores values above 1.0 as they
    // are, and the sRGB encoding is not its business.
    return vec4<f32>(color, 1.0);
```

## Tone mapper

```text
linear HDR ──→ ×exposure ──→ Reinhard ──→ linear SDR ──→ sRGB encode ──→ surface
  (может > 1)     (скаляр)     c/(1+c)     ([0, 1))        (один раз)

Контрольные числа Reinhard:
  вход 0 → 0        вход 1 → 0.5      вход 4 → 0.8
  exposure 2:       вход 4 → 8 → 8/9
```

На обычный экран — SDR, standard dynamic range, стандартный динамический диапазон — значения ярче единицы не вывести: их нужно **отобразить** в [0, 1].
Fullscreen-проход из [главы о промежуточной текстуре](../render-to-texture/) превращается в tone mapper: сначала умножение на экспозицию, затем оператор **Reinhard** `c / (1 + c)`:

```wgsl
    // Exposure is a plain multiplier before the operator; Reinhard
    // compresses every positive value into [0, 1): 0 -> 0, 1 -> 0.5,
    // 4 -> 0.8.
    let scaled = hdr.rgb * tone.exposure;
    let tone_mapped = scaled / (vec3<f32>(1.0) + scaled);
    // Linear SDR out: the sRGB surface encodes it once, on store.
    return vec4<f32>(tone_mapped, 1.0);
```

Каждое положительное значение оператор сжимает в [0, 1), не достигая единицы (контрольные числа — на диаграмме выше).
Экспозиция — множитель **до** оператора: при exposure 2 значение 4 превращается не в Reinhard(4) + 2, а в Reinhard(8) = 8/9.
Оба числа — объект проверки ниже.

Порядок важен и в конце: тонмаппер выдаёт линейный SDR, а единственное sRGB-кодирование выполняет поверхность.
Linear 0.5 кодируется в sRGB ≈ 0.735 **один раз**; двойное кодирование дало бы sRGB(0.735) ≈ 0.873 — кадр выцвел бы.

## Экспозиция и интенсивность

Клавиши не трогают геометрию и формулу — только два числа:

- `[` / `]` гоняют экспозицию по циклу 0.5 / 1 / 2 / 4 — тот же HDR-кадр выглядит светлее или темнее;
- `I` переключает интенсивность света 0.6 ↔ 4.0. Без тонмаппера яркость 4.85 просто обрезалась бы в белый потолок; с Reinhard центр и окружение остаются различимыми: блик `4.85/5.85 ≈ 0.83` против `2.05/3.05 ≈ 0.67` вокруг (при слабом свете те же точки давали `0.44` и `0.26`). Разницу видно **только через tone mapper**.

Это и есть смысл HDR: значения ярче единицы существуют *до* вывода и сохраняют порядок.

## Диагностика clipping

Где кадр покинул SDR-диапазон? Клавиша `D` включает режим, который отвечает буквально:

```wgsl
    if (tone.mode == 1u) {
        // Clipping view: white wherever the linear frame left the SDR
        // range before tone mapping, black everywhere else.
        let peak = max(hdr.r, max(hdr.g, hdr.b));
        let clipped = select(0.0, 1.0, peak > 1.0);
        return vec4<f32>(vec3<f32>(clipped), 1.0);
    }
```

Белым отмечены пиксели, где линейное значение до tone map больше 1, чёрным — всё остальное.
При интенсивности главы (0.6) маска пуста: максимум сцены ≈ 0.77 и диапазон SDR ещё не покинут — на `I` (интенсивность 4) центр и заметное пятно вокруг него уходят за 1 и подсвечиваются. `select` здесь вместо `if`: выбор двух констант — ветвление не нужно.

Reinhard — учебный оператор, а не обещание фотометрической точности: он спрессовывает и яркие, и тёмные участки, теряя контраст посередине; сравнение операторов — отдельная тема.

## Снимок

```sh
cargo run -p hdr-output
cargo test -p foundations-verify --test hdr_output
```

Проверка зеркалит формулу Blinn–Phong на CPU (как в [главе «Материал и блик»](../../space-light/blinn-phong/)), прогоняет результат через экспозицию и Reinhard и сравнивает байт центра кадра: при exposure=1 и интенсивности 0.6, затем при exposure=2 — по формуле Reinhard(2c).
Отдельные шаги включают интенсивность 4.0: clipping-вид обязан показать центр белым и фон чёрным, а обычный — дать Reinhard(4.85) < 255.

![HDR-сцена при интенсивности 4: слева диагностическая маска выхода за 1.0, справа Reinhard.](/results/hdr-output-clip-reinhard.png)

Одна и та же HDR-сцена при одинаковой экспозиции (интенсивность 4): слева диагностическая маска — белым помечены пиксели, чей линейный свет выше 1 (не «отсечённый цвет», а карта выхода за диапазон); справа Reinhard сжимает диапазон, сохраняя различимыми и яркий центр, и тени. Жёсткая отсечка цветов (`clamp`) дала бы белое пятно там же, где маска, но с потерей всех промежуточных значений.

## Проверьте модель

1. Почему промежуточный кадр — `Rgba16Float`, а не `Rgba16Unorm` и не sRGB-формат?
2. Что изменится в кадре, если умножение на экспозицию перенести *после* Reinhard?
3. Reinhard никогда не выдаёт 1.0. Почему это свойство, а не дефект для HDR-вывода?
4. Кадр дважды закодирован в sRGB (промежуточно и на поверхности). Каким станет linear 0.5 и почему это видно?

::: details Решения и контрольные выводы

1. Unorm останавливается на 1.0 — тот же clamp, от которого мы уходили; sRGB-варианта у float-форматов нет, а кодирование должно случиться один раз — на выводе.
2. Exposure перестанет менять форму сжатия: Reinhard(c)·k при большом c всё равно стремится к k, но тёмные участки, где оператор почти линеен, изменятся сильнее ярких — порядок «умножение до оператора» выбран как простая модель камеры.
3. Оператор отображает [0, ∞) в [0, 1): значение 1.0 — недостижимый предел, а не потеря; на sRGB-поверхности и не нужен (байт 255 получается кодированием значений вблизи 1).
4. sRGB(0.5) ≈ 0.735, повторное кодирование: sRGB(0.735) ≈ 0.873 — пиксель неоправданно посветлеет; именно поэтому промежуточный кадр линейный, а кодирует только поверхность.

:::
