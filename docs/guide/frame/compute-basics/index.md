# Базовый compute

::: info Только native
Оболочка и офскрин-стенд проверки прежние; в кадре появляется проход нового рода — compute. Стенд независим: никакой камеры и сцены, только полоса индикаторов внизу экрана.
:::

До сих пор каждый байт, который видит шейдер, приезжал с CPU: вершины, uniform'ы, текстуры.
Вопрос главы: что если данные **рождает сам GPU** — и тут же рисует их в том же кадре?
Для этого у WebGPU есть второй род прохода: compute.

**Эксперимент:** compute-проход заполняет буфер из 257 значений `i/256`; render-проход того же кадра показывает их полосой из 257 индикаторов — высота и яркость каждой ячейки и есть значение.
Клавиша `R` повторяет заполнение с 256 значениями.

## Полоса, которую красит не CPU

Значения пишет GPU — значит, CPU их не видит: чтение результатов обратно на CPU — отдельная тема (и отдельная глава), здесь её нет.
Покрасить индикаторы на CPU невозможно в принципе — и не нужно: вершинный этап умеет читать массивы напрямую.
Это тот самый [vertex pulling](../../foundations/vertex-pulling/), только массив теперь не статичная геометрия, а свежие данные кадра.

Меш полосы генерируется на CPU один раз: 257 квадов по 4 вершины, у каждой вершины два атрибута — положение угла внутри ячейки и номер самой ячейки. Запись занимает ровно 12 байт и упакована плотно: раскладку задаёт **явный** контракт vertex fetch — CPU определяет `format`/`offset`/`stride`, правила WGSL-структур на эти байты не влияют. Разбор обеих раскладок — в главах [«Read-only storage и vertex pulling»](../../foundations/vertex-pulling/) и [«Смешанные поля»](../../foundations/uniform-params/).

```rust
/// One corner of one indicator cell: which cell it belongs to and where
/// inside the cell it sits.
#[repr(C)]
#[derive(Clone, Copy, bytemuck::Pod, bytemuck::Zeroable)]
struct Vertex {
    /// (0 or 1, 0 or 1): horizontal side within the cell, vertical side of
    /// the value-scaled height. The record is packed tight: vertex fetch
    /// reads by the explicit offsets below, not by WGSL struct rules.
    corner: [f32; 2],
    cell: u32,
}
```

Вершинный шейдер достаёт значение своей ячейки из storage и делает из него сразу и позицию, и цвет — фрагментному остаётся только вернуть серый:

```wgsl
    // Cells at and beyond the count stay empty: the compute pass never
    // wrote them, so the pulled value would be stale.
    let value = select(0.0, VALUES[input.cell], input.cell < params.count);
    let x = X0 + (f32(input.cell) + input.corner.x) * (STRIP_WIDTH / CELLS);
    let y = Y0 + input.corner.y * value * STRIP_HEIGHT;
```

Тонкость этой строки: `select` — не «короткозамкнутый» `if`. Оба его операнда-значения вычисляются всегда, включая `VALUES[input.cell]` для выключенной ячейки. Чтение здесь законно по другой причине: буфер выделён под все 257 ячеек, и любой `input.cell` попадает в его границы — выключенная ячейка читает лишь не записанное в этом кадре значение (буферы WebGPU стартуют нулями), которое `select` и отбрасывает. Если бы индекс мог выйти за длину массива, спасло бы только настоящее ветвление `if` или ограничение индекса — не `select`.

## Compute pipeline

У compute-шейдера нет ни вершин, ни растеризации: только функция и номер её запуска.
Один запуск функции — один **invocation**; 64 запуска образуют **workgroup**.

```wgsl
@group(0) @binding(0) var<storage, read_write> VALUES: array<f32>;
@group(0) @binding(1) var<uniform> params: Params;

@compute
@workgroup_size(64)
fn fill(@builtin(global_invocation_id) id: vec3<u32>) {
    if (id.x < params.count) {
        VALUES[id.x] = f32(id.x) / f32(params.count - 1u);
    }
}
```

`@builtin(global_invocation_id)` — уникальный индекс запуска: invocation с `id.x = k` пишет ровно слот `k`.
Отсюда и порядок в одном dispatch не нужен: у каждого запуска свой адрес записи, конфликтов нет — а общего порядка между запусками WebGPU и не обещает.

Два новых элемента привязки:

- `var<storage, read_write>` — массив, который compute **меняет**: до сих пор все наши storage были `read`;
- `params.count` — uniform: сколько значений заполнять и каков знаменатель.
  Отдельный `u32` — законная uniform-запись и в 4 байта: ограничения uniform-адресного пространства (глава [«Смешанные поля»](../../foundations/uniform-params/)) касаются массивов и вложенных структур, а не одиночного скаляра; `i/256` при 257 значениях превращается в `i/255` при 256, и оба числа едут в кадр одним буфером.

## Dispatch: 5 групп, 320 запусков, 63 лишних

```text
dispatch_workgroups(5, 1, 1) при workgroup_size(64):

группа 0:  [0 ......... 63]   ← 64 полезных
группа 1:  [64 ...... 127]   ← 64 полезных
группа 2:  [128 ..... 191]   ← 64 полезных
группа 3:  [192 ..... 255]   ← 64 полезных
группа 4:  [256 ....... 319] ← 1 полезный + 63 лишних
                                 (id.x < 257 → пропуск)

итого: 320 invocations, 257 записей, 63 пустых запуска
```

Размер запуска кратен workgroup: попросить «ровно 257 запусков» нельзя.
Считаем группы с округлением вверх и запускаем:

```rust
            let groups = self.count.div_ceil(WORKGROUP_SIZE);
            pass.dispatch_workgroups(groups, 1, 1);
```

257 значений → `⌈257/64⌉ = 5` групп → **320 invocations, из них 257 полезных, 63 лишних**.
Лишние — это `id.x` от 257 до 319: проверка `id.x < params.count` превращает их в пустые запуски.
Без неё invocation с `id.x = 257` вышел бы за границу массива — а выход за границу в WGSL не «безобидный лишний байт»: это динамическая ошибка. Реализация обязана лишь не дать доступу уйти за пределы привязанного буфера — запись может попасть в любое место буфера (затерев чужое значение) или не выполниться, а чтение вернуть любое значение из буфера. Конкретное поведение не обещано и разное на разных GPU — валидная программа за границу не выходит вовсе, и bounds check — часть алгоритма, а не страховка на всякий случай.

Клавиша `R` меняет `count` на 256: теперь достаточно **4 групп ровно** (256 кратно 64), знаменатель — 255, а ячейка 256 пуста — `select` отбрасывает её прочитанное значение (само чтение законно: буфер покрывает все 257 ячеек), и высота ячейки остаётся нулевой.

## Кто пишет, кто читает

Граф кадра: **compute → буфер → render**.
Буфер один, привязок две, и они не смешиваются: compute-проход пишет через `read_write`, render-проход читает через `read`-only в вершинной стадии — два bind group layout, два bind group.

Разделение не вкусовое: смешивать `read_write` и `read` одного буфера в одном проходе запрещено контрактом; наши проходы разные — поэтому и layout'а два.
Проходы идут одним кодировщиком в порядке записи: сначала compute, потом render — между проходами порядок гарантирован самим API, никаких барьеров руками.

Перед созданием ресурсов проверяем лимит устройства. Фактическая потребность — по одному storage-буферу на стадию: compute-проход пишет через `read_write`, вершинная стадия читает через `read`:

```rust
        if gpu.device.limits().max_storage_buffers_per_shader_stage < 1 {
            return Err("This example requires at least one storage buffer per shader stage".into());
        }
```

Порог — ровно потребность; лимит по умолчанию (8) перекрывает её с многократным запасом.

Сам буфер — 257 × 4 = 1028 байт — живёт целиком на GPU: ни одной CPU-записи после создания.

## Проверьте модель

1. Почему для 257 значений нужно 5 групп, а для 256 — ровно 4?
2. Что произойдёт, если убрать проверку `id.x < params.count`?
3. Почему цвет индикаторов обязан вычислять шейдер, а не CPU?
4. Зачем одному буферу два bind group layout, если данные одни?

::: details Решения и контрольные выводы

1. Количество запусков кратно размеру группы 64: `⌈257/64⌉ = 5` (320 запусков), 256 = 4 × 64 — без остатка.
2. Invocations 257..319 попытались бы записать `VALUES[id.x]` за границей массива длины 257. Это динамическая ошибка: реализация может отправить запись в любое место буфера или отбросить её — поведение не специфицировано. Настоящие 257 значений при этом, скорее всего, остались бы целы, но полагаться на «скорее всего» нельзя: границу держит bounds check, потому что программа, выходящая за неё, невалидна.
3. CPU не читает буфер: значения созданы и потреблены на GPU внутри одного кадра. Readback — тема будущей главы, здесь его нет.
4. Привязка в проходе имеет одно имя доступа: compute пишет (`read_write`), вершинная стадия читает (`read`). Разные проходы и разный доступ — два layout'а; смешение доступа одного буфера в одном проходе контракт запрещает.

:::

GPU умеет заполнять данные сам — этого достаточно, чтобы рисовать результат.
