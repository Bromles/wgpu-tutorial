# MSAA и resolve

::: info Только native
Снимок [главы «Ориентация и видимость»](../../space-light/depth-culling/): те же два пересекающихся треугольника, тот же depth-паттерн. Новое — сколько сэмплов считает растеризатор и куда девается лишнее. Клавиша `M` переключает 1↔4.
:::

Край треугольника идёт по диагонали, а пиксели — квадратная сетка: силуэт превращается в лестницу.
Причина проста: **на каждый пиксель даётся один ответ** — либо цвет треугольника, либо цвет фона, смотря где оказался центр пикселя.

MSAA (multisample anti-aliasing) добавляет пикселю точности ровно там, где решается этот вопрос.

## Сэмпл покрытия и вызов фрагмента

MSAA различает две вещи, которые до сих пор совпадали:

- **coverage-сэмплы** — фиксированные точки внутри пикселя. WebGPU не задаёт их позиции; типовые реализации 4× используют сетку со смещениями ±0.125/±0.375 от центра. Растеризатор проверяет накрытие треугольником для каждой точки отдельно;
- **вызов фрагмента** — исполнение шейдера. По умолчанию он запускается **один раз на пиксель**, и его результат реплицируется во все накрытые сэмплы.

```wgsl
@fragment
fn fs_main(input: VertexOutput) -> @location(0) vec4<f32> {
    // One invocation per covered pixel: the single result value is
    // replicated into every covered sample by the rasterizer.
    return vec4<f32>(input.color, 1.0);
}
```

Шейдер сцены не изменился ни на строчку: цвет по-прежнему один на пиксель — меняется только подсчёт края.
«Один вызов на пиксель» — это один вызов на пиксель **на примитив**: два перекрывающихся треугольника дают до двух вызовов в пикселе пересечения. Ещё одно следствие: сэмплы покрытия рассеяны шире центра, поэтому при count=4 могут накрываться пиксели, чьи центры при count=1 не накрывались — край не только сглаживается, но и чуть раздвигается.

## Resolve

Сэмплы живут в **мультисэмпловой текстуре**: один тексель хранит четыре цвета (по одному на сэмпл).
Читать такую текстуру в шейдере мы не будем — вместо этого проход **сводит** (resolve) её в обычную односэмпловую: среднее **всех четырёх** сэмплов становится одним пикселем. Усредняются и сэмплы, оставшиеся от очистки или другой геометрии: ненакрытый сэмпл несёт цвет очистки — именно он разбавляет край до полутонов.
Цель сведения задаётся прямо во вложении прохода:

```rust
                color_attachments: &[Some(RenderPassColorAttachment {
                    view: color_view,
                    resolve_target,
                    ops: Operations {
                        load: LoadOp::Clear(CLEAR),
                        // Resolve happens at pass end regardless; the MSAA
                        // texture itself is never read again, so in the
                        // multisampled mode its store can be discarded.
                        store: if resolve_target.is_some() {
                            StoreOp::Discard
                        } else {
                            StoreOp::Store
                        },
                    },
                    depth_slice: None,
                })],
```

У `resolve_target` три жёстких требования: ровно **один сэмпл**, **тот же формат**, что у вложения, и usage **`RENDER_ATTACHMENT`** — сводить можно только туда, куда можно рисовать.
`store` при этом управляет самой мультисэмпловой текстурой, а не результатом сведения: сведение выполняется в конце прохода и пишет односэмпловую цель; раз MSAA-текстура после этого не читается, в мультисэмпловом режиме её хранить незачем — `Discard`. В односэмпловой ветке цели сведения нет, и результат обязан сохраниться обычным `Store`.
В режиме count=1 у вложения та же односэмпловая текстура стоит на месте `view`, а `resolve_target: None` — сводить нечего.

Эксперимент повторяет схему [«Промежуточный кадр»](../render-to-texture/): сцена рисуется в промежуточный кадр, fullscreen-проход переносит его на поверхность.
Единственное решение — куда рисует первый проход:

```text
count = 1:  сцена → односэмпловый кадр (без resolve)      → fullscreen → surface
count = 4:  сцена → мультисэмловая пара + resolve в кадр → fullscreen → surface
```

Финальный fullscreen-проход всегда односэмпловый: сглаживается геометрия сцены, а не копирование готового кадра.

## Согласованный комплект

Количество сэмплов — это состояние pipeline, поэтому переключение по `M` — это смена pipeline, а не параметр прохода.
Оба существуют заранее и различаются одной строкой:

```rust
            // The whole point: the pipeline declares how many samples the
            // pass will have. Everything else about the pipeline is
            // identical between the two modes.
            multisample: wgpu::MultisampleState {
                count: sample_count,
                ..Default::default()
            },
```

Вложение должно согласиться с pipeline — и цвет, и **глубина**: у count=4 глубина тоже count=4, иначе валидация отклонит проход.

```rust
        // The depth attachment follows the color attachment: a count = 4
        // pass needs count = 4 depth, or validation fails.
        let msaa_depth = gpu.device.create_texture(&TextureDescriptor {
            label: Some("MSAA depth"),
            size,
            mip_level_count: 1,
            sample_count: SAMPLE_COUNTS[1],
            dimension: TextureDimension::D2,
            format: TextureFormat::Depth32Float,
            usage: TextureUsages::RENDER_ATTACHMENT,
            view_formats: &[],
        });
```

Весь комплект — односэмпловый кадр (он же resolve-цель), односэмпловая глубина, мультисэмловый цвет и мультисэмловая глубина — пересоздаётся по знакомому паттерну `pending_size → recreate` из [«Промежуточный кадр»](../render-to-texture/), вместе с view и bind group финального прохода.

## Гарантия вместо запроса

Можно ли спросить устройство о поддержке заранее?
В wgpu 30 запрос есть — `guaranteed_format_features` сообщает поддерживаемые sample counts каждого формата, — но для этой главы он не нужен: **`Rgba8Unorm` и `Depth32Float` с count=4 гарантированы базовым уровнем WebGPU**, поэтому текстуры создаются без проверки. В обработке изображения мы фиксировали контракт кодом даже для базовой возможности; здесь проверка избыточна — оба формата покрыты гарантией.
Гарантия покрывает 1× и 4×; count 8× базовой гарантией не покрывается — понадобится запрос возможностей адаптера.

## Что именно сглаживается

Пиксель на силуэте, где белый треугольник накрыл два сэмпла из четырёх, после resolve хранит linear 0.5 — как если бы фон был чёрным, а треугольник белым.
Кодирование одно, на поверхности: linear 0.5 → sRGB ≈ 0.735 → байт 188.
Вместо резкой ступени «255 или фон» появляется промежуточный цвет — и лестница превращается в плавный край.

У MSAA есть честная граница: сэмплы — геометрические точки. Мелкая текстура, сплывающая в шум при минификации, продолжит мерцать — это **текстурный алиасинг**, его лечат фильтрация и mip-уровни из [главы «UV и фильтр»](../../foundations/texture-sampling/), а не количество сэмплов.

## Снимок

```sh
cargo run -p msaa-resolve
cargo test -p msaa-resolve
```

Неподвижный кадр, `M` переключает count: меняется покрытие силуэта, не геометрия.

![Диагональный край: слева count 1, справа count 4.](/results/msaa-resolve-1x-4x.png)

Диагональный силуэт: слева при count=1 каждый пиксель отвечает «треугольник или фон» — лестница; справа при count=4 resolve смешал частично покрытые пиксели в промежуточные оттенки.
Внутренности треугольников не изменились — сгладился только край.

Проверка зондирует внутренности обоих треугольников (оба режима обязаны дать байт в байт одинаковые чистые цвета), затем проходит полосой строк через правый диагональный край: при count=4 появляются смешанные пиксели, и «чисто фоновых» становится строго меньше, чем при count=1; вдали от края оба кадра совпадают.

## Проверьте модель

1. Почему шейдер сцены не изменился при переходе от одного сэмпла к четырём?
2. Какие три ресурса обязаны согласовать sample count, и что случится с глубиной, если забыть?
3. Пиксель накрыт двумя сэмплами из четырёх белым треугольником на чёрном фоне. Какой байт хранит односэмпловый кадр после resolve?
4. Почему MSAA не спасает мерцающую вдали полосатую текстуру?

::: details Решения и контрольные выводы

1. Фрагмент по-прежнему вызывается один раз на пиксель, и его цвет реплицируется в накрытые сэмплы; MSAA меняет подсчёт покрытия и сведение, а не формулу цвета.
2. Цветовое вложение, depth-вложение и pipeline. Глубина count=1 в проходе count=4 — ошибка валидации: вложения прохода обязаны соответствовать `MultisampleState` pipeline.
3. Resolve усредняет все четыре сэмпла в линейном свете: 2 накрытых несут белый (1.0), 2 ненакрытых — чёрную очистку (0.0); среднее 2/4 · 1.0 = 0.5 линейного. Промежуточный односэмпловый кадр `Rgba8Unorm` хранит это как байт ≈ 128; поверхность вывода кодирует его в sRGB один раз при выводе — итоговый байт ≈ 188. Цепочка целиком: coverage → цвета сэмплов → линейное усреднение (UNORM) → одно sRGB-кодирование.
4. Текстурный алиасинг — это выбор неверного текселя при сжатии изображения, а не потеря покрытия. Сэмплы не умножают текстурные выборки: чтение идёт по UV пикселя, mip-уровень выбирается по производным UV в его центре — обычная фильтрация, которую MSAA не заменяет.

:::

Кадр научился быть гладким по краям.
