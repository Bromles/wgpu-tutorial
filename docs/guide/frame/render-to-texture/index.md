# Промежуточный кадр: render-to-texture

::: info Только native
Снимок [«Тексели и upload»](../../foundations/texture-load/): тот же размеченный прямоугольник, те же UV и clip-координаты. Новое — куда он рисуется и каким путём попадает на экран.
:::

Каждый кадр до сих пор летел прямо на поверхность: один render pass, один output.
Но следующие задачи маршрута — обработка кадра и тени — требуют читать отрендеренное как данные. Куда положить готовый кадр, пока его никто не показал?
Законченный кадр — это просто изображение, а изображение можно **нарисовать во что-то, кроме окна**: в текстуру. И тогда следующий проход прочитает его как вход.

Граф из [главы «Базовый compute»](../compute-basics/) продолжается: там буфер писался compute-проходом и читался рендером, здесь отрендеренный кадр становится текстурой и читается финальным проходом:

```text
render → промежуточная текстура → fullscreen pass → surface
```

**Эксперимент:** прямоугольник 2×2-текстуры из [главы «Тексели и upload»](../../foundations/texture-load/) рисуется сначала в offscreen-текстуру, затем один fullscreen-треугольник переносит её на поверхность попиксельно, без фильтрации.
Кадр обязан совпасть с прямым путём байт в байт.

## Промежуточная текстура

Три решения — формат, usage и размер:

```rust
        let texture = gpu.device.create_texture(&TextureDescriptor {
            label: Some("Intermediate frame"),
            size: Extent3d {
                width,
                height,
                depth_or_array_layers: 1,
            },
            mip_level_count: 1,
            sample_count: 1,
            dimension: TextureDimension::D2,
            // Linear RGBA8Unorm: values stay linear between the passes.
            format: TextureFormat::Rgba8Unorm,
            usage: TextureUsages::RENDER_ATTACHMENT | TextureUsages::TEXTURE_BINDING,
            view_formats: &[],
        });
```

- **`Rgba8Unorm`, не sRGB.** Промежуточный кадр хранит линейные значения; sRGB-кодирование происходит один раз — при выводе на поверхность.
  Возьмите сюда sRGB-формат — и каждый проход цепочки кодировал бы и декодировал зря;
- **`RENDER_ATTACHMENT | TEXTURE_BINDING`** — первое разрешает рисовать в текстуру, второе привязывать её к шейдеру;
- **размер — физические пиксели окна**: один тексель должен соответствовать одному пикселю, иначе fullscreen-проход растянет или обрежет кадр.

Первый проход рисует прямоугольник в эту текстуру: тот же меш, тот же шейдер, что и раньше, — меняется только цель:

```rust
                    // Linear target: the intermediate frame keeps linear
                    // values; the sRGB encoding happens only at the final
                    // output, in the fullscreen pass.
                    targets: &[Some(ColorTargetState {
                        format: TextureFormat::Rgba8Unorm,
```

`store: StoreOp::Store` у вложения — не формальность: кадр должен **пережить проход**, его же будет читать следующий.

## Fullscreen-треугольник

Второму проходу нужно покрыть весь экран.
Квадрат — четыре вершины и два треугольника; но достаточно одного треугольника, выходящего за пределы clip-квадрата: вершины `(-1,-1)`, `(3,-1)`, `(-1,3)` покрывают его целиком, а отсечение делает своё дело бесплатно.
Позиции лежат в массиве прямо в шейдере — вершинного буфера у прохода нет вовсе:

```wgsl
@vertex
fn vs_full(@builtin(vertex_index) vertex_index: u32) -> @builtin(position) vec4<f32> {
    var positions = array<vec2<f32>, 3>(
        vec2<f32>(-1.0, -1.0),
        vec2<f32>(3.0, -1.0),
        vec2<f32>(-1.0, 3.0),
    );
    return vec4<f32>(positions[vertex_index], 0.5, 1.0);
}
```

Интерполировать нечего — и не нужно: координату даёт сам фрагмент.

## Центры текселей

Перенос — не «копия области», а чтение одного текселя на один пиксель:

```wgsl
@fragment
fn fs_full(@builtin(position) position: vec4<f32>) -> @location(0) vec4<f32> {
    // Pixel centers and texel centers coincide: truncating the fragment
    // position (pixel + 0.5) addresses exactly the texel (x, y).
    let texel = vec2<i32>(position.xy);
    return textureLoad(FRAME, texel, 0);
}
```

`@builtin(position)` фрагмента — это `(пиксель + 0.5)`: центры.
Отбрасывая дробную часть, получаем `(x, y)` — и это ровно тот тексель, центр которого совпадает с центром пикселя при равных размерах.
Ни сэмплера, ни фильтрации — `textureLoad` читает целые тексели, а сдвиг на полтекселя здесь невозможен в принципе: координаты не масштабируются.

Сравните пути: при прямой отрисовке фрагмент писал цвет текселя в пиксель поверхности; здесь он пишет его в промежуточный тексель, а fullscreen-фрагмент переносит байт дальше — sRGB-кодирование остаётся однократным, на поверхности (см. выше).
Разница путей — одно округление UNORM (не более 1/255 на канал) при записи в промежуточный байт: это свойство хранения, а не ошибка координат; на квадрантах с кодами 255/0 итоговые байты совпадают.

## Resize

Размер текстуры привязан к размеру цели, а цель меняется.
Знакомый по depth-attachments [паттерн](../../space-light/depth-culling/): событие запоминается, ресурс пересоздаётся в начале следующего `draw` — и вместе с ним всё зависимое: view и bind group, ведь старые смотрят на старую текстуру:

```rust
    /// Sets the next target size without waiting for a window event; also
    /// the hook the offscreen harness uses before its first draw.
    pub fn resize(&mut self, width: u32, height: u32) {
        if width > 0 && height > 0 {
            self.pending_size = Some(PhysicalSize::new(width, height));
        }
    }
```

Нулевой размер (свёрнутое окно) просто не доходит до пересоздания — кадр пропускается раньше, во фреймворке.

![Эталонный кадр render-to-texture: четыре квадранта на сером фоне — совпадает с прямым путём.](/results/render-to-texture.png)

Проверка сравнивает кадр с эталоном, зондирует все четыре подписанных угла (ориентация не перевернулась), заглядывает на границу «пиксель в квадрате / пиксель из квадрата» (нет сдвига на полтекселя) и повторяет контрольные углы во втором размере — путь пересоздания ресурсов обязан дать тот же кадр.
Интерактивно попробуйте неудобный размер вроде 641×359: отображение остаётся точным, ресурсы получают именно этот размер.

## Проверьте модель

1. Почему промежуточная текстура — `Rgba8Unorm`, а не `Rgba8UnormSrgb`, хотя поверхность — sRGB?
2. Почему fullscreen-треугольнику хватает трёх вершин, и где «прячется» четвёртый угол экрана?
3. Что изменится в кадре, если `fs_full` возьмёт `vec2<i32>(position.xy) - vec2<i32>(1)`?
4. Какие три ресурса приходится пересоздавать вместе при resize и почему?

::: details Решения и контрольные выводы

1. Кодирование sRGB — операция вывода, оно должно случиться один раз, на поверхности. sRGB-промежуточная текстура кодировала бы на записи и декодировала при чтении — двойная работа и потеря точности.
2. Вершины выходят за clip-квадрат: гипотенуза из `(3,-1)` в `(-1,3)` проходит через `(1,1)` — правый верхний угол. Отсечение за пределами кадра делает сам растеризатор.
3. Все чтения сдвинутся на тексель влево-вверх, у правой и нижней границы появятся «недостающие» тексели. Чтение за границей текстуры не обещает конкретного значения: может вернуться любой тексель внутри текстуры или нулевой вектор — кайма в один тексель, не обязательно чёрная. Повторных текселей с противоположной стороны не будет: адресация `textureLoad` не заворачивается. Это и есть сдвиг на целый тексель; полтекселя при целочисленном `textureLoad` не возникает.
4. Текстура, view и bind group: view принадлежит текстуре, bind group держит view. Новая текстура — новые зависимости, старые указывают на освобождённое изображение.

:::

Кадр стал входом — теперь его можно и **обрабатывать**.
