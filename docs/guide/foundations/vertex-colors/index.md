# Интерполяция

::: info Только native
Продолжаем маршрут через [фреймворк](../framework-triangle/): окно и lifecycle уже не меняются.
:::

Треугольник пока был одноцветным.
Как получить плавный переход цвета — и почему у края он именно такой?
В этой главе у каждой вершины появляется свой цвет, а кадр — градиент.

**Эксперимент:** прежний треугольник и фон; сплошной белый заменён тремя линейными цветами вершин: красный `(-0.75, -0.75)`, зелёный `(0.75, -0.75)`, синий `(0, 0.75)`.
Изучаемая величина — точка внутри треугольника: предсказанный по модели цвет сверяется с кадром.
Compile-time константа в шейдере переключает градиент и сплошной цвет [главы «От трёх точек к треугольнику»](../first-triangle/) (сравнение требует пересборки).

```sh
cargo run -p vertex-colors
cargo test -p foundations-verify
```

## Веса на отрезке

Начнём с двух точек.
Пусть значение меняется от `a` к `b`, а параметр `t ∈ [0, 1]` задаёт пройденную долю пути.
Линейная интерполяция смешивает их двумя весами:

```text
value(t) = (1 - t) · a + t · b        веса: 1 - t и t, в сумме 1
```

Веса — это доли: при `t = 0` весь вклад у `a`, при `t = 1` — у `b`, при `t = 0.5` вклады равны.
Если `a` и `b` — векторы (например, RGB), операция применяется покомпонентно: сложение векторов и умножение на скаляр действуют на каждый компонент отдельно.
Это компонентное расширение уже знакомой арифметики.

Смешиваются линейные значения.
Кодирование sRGB — нелинейное, поэтому «средний код» двух цветов не равен коду среднего цвета; этот разрыв дословно вернётся в главе о цветовом кодировании.

## Три веса: площади

Внутри треугольника одного параметра мало.
Возьмём точку `P` и соединим её с вершинами `A`, `B`, `C`: треугольник распадается на три подтреугольника.

<BarycentricDiagram />

**Барицентрические координаты** — тройка весов, задающих вклад вершин:

```text
w_A = S(P, B, C) / S(A, B, C)        вес вершины A — доля площади напротив неё
w_B = S(P, C, A) / S(A, B, C)
w_C = S(P, A, B) / S(A, B, C)
w_A + w_B + w_C = 1
```

Три подтреугольника без промежутков и перекрытий составляют исходный треугольник, поэтому сумма площадей — а значит и весов — равна единице.
Цвет в точке `P` — то же смешивание, что на отрезке, но с тремя весами:

```text
color(P) = w_A · color_A + w_B · color_B + w_C · color_C
```

Контрольные точки нашего стенда:

- середина красно-зелёного ребра: `P = (0, -0.75)` делит нижние подтреугольники так, что `w_A = w_B = 0.5`, `w_C = 0` → линейный цвет `(0.5, 0.5, 0)`;
- центроид (пересечение медиан): все три площади равны → `w = (1/3, 1/3, 1/3)` → линейный цвет `(1/3, 1/3, 1/3)`.

Равные веса в центроиде — следствие равных площадей, а не «равноудалённости» от вершин.
Формулу площади `S(A, B, C) = ½·|(B−A) × (C−A)|` выводит глава [«Три измерения и базис»](../../space-light/basis3d/) из векторного произведения; здесь достаточно отношения площадей.

## WGSL: struct выхода и @location

Цвет нужно доставить из вершинного шейдера во фрагментный через растеризацию; для этого шейдер возвращает структуру с помеченными полями.
Шейдер главы целиком (`src/shader.wgsl`):

```wgsl
// Same clip-space positions as before, but each vertex now carries its own
// linear RGB; the GPU interpolates them across the covered samples.
const POSITIONS: array<vec4<f32>, 3> = array(
    vec4<f32>(-0.75, -0.75, 0.5, 1.0),
    vec4<f32>(0.75, -0.75, 0.5, 1.0),
    vec4<f32>(0.0, 0.75, 0.5, 1.0),
);

// Red at the bottom-left, green at the bottom-right, blue at the top.
const COLORS: array<vec3<f32>, 3> = array(
    vec3<f32>(1.0, 0.0, 0.0),
    vec3<f32>(0.0, 1.0, 0.0),
    vec3<f32>(0.0, 0.0, 1.0),
);

// Chapter 04 fallback color for the solid mode.
const SOLID_COLOR: vec4<f32> = vec4<f32>(1.0, 1.0, 1.0, 1.0);

// Compile-time experiment switch: gradient vs the solid color of chapter 04.
// Changing this value requires a rebuild; it is not a runtime parameter.
const GRADIENT: bool = true;

// Struct returned by the vertex stage. @location(0) marks the field that is
// interpolated across the primitive for each fragment; @builtin(position)
// stays the clip-space position consumed by rasterization.
struct VertexOutput {
    @builtin(position) position: vec4<f32>,
    @location(0) color: vec3<f32>,
};

@vertex
fn vs_main(@builtin(vertex_index) vertex_index: u32) -> VertexOutput {
    var output: VertexOutput;
    output.position = POSITIONS[vertex_index];
    output.color = select(SOLID_COLOR.rgb, COLORS[vertex_index], GRADIENT);
    return output;
}

// The interpolated color arrives in the same struct: the fragment reads the
// per-fragment value of @location(0), not the vertex value.
@fragment
fn fs_main(input: VertexOutput) -> @location(0) vec4<f32> {
    return vec4<f32>(input.color, 1.0);
}
```

Новое по сравнению с [главой «От трёх точек к треугольнику»](../first-triangle/):

- **struct** собирает несколько значений в один тип с именованными полями; функция возвращает его целиком.
- `var output: VertexOutput;` — локальная изменяемая переменная (в отличие от `const` на уровне модуля); поля заполняются по одному, `return` отдаёт значение.
- Атрибут `@location(0)` на поле `color` — это интерфейс между стадиями: значение, вычисленное вершинным шейдером, **интерполируется** по примитиву, и фрагментный шейдер получает своё значение для каждой покрытой выборки.
- Фрагментный шейдер принимает ту же структуру, но данные в ней новые — веса, пересчитанные для конкретного фрагмента.
- `select(a, b, cond)` — выбор значения по булеву условию; с константным `GRADIENT` компилятор оставит ровно одну ветку.

Интерполяция — свойство `@location`-атрибутов: любой вектор или число в такой структуре поедет по тем же барицентрическим весам.
Для дискретных величин — например, номера вершины — такое смешивание бессмысленно; WGSL позволяет пометить атрибут `@interpolate(flat)`, и тогда фрагмент получает значение без интерполяции (по правилам — от «вызывающей» вершины).
Оно нам пока не нужно, но термин зафиксируем: **flat** — дискретно, без смешивания.

Позиция не входит в общий интерполируемый набор: у неё своя роль и своё соглашение.
Случай `w = 1` всех вершин делает веса барицентрической интерполяции в экранном пространстве точными; перспективный случай изменит и это — тема главы о проекции.

## Проверьте модель

1. Не запуская программу, вычислите линейный цвет середины красно-синего ребра. Какой sRGB-код ожидается по каждому каналу?
2. Верна ли мысль: «веса в центроиде равны, потому что центроид равноудалён от вершин»? Проверьте её на стенде: центроид — `(0, -0.25)`, посчитайте расстояния до трёх вершин.
3. Пересоберите с `GRADIENT = false`. Что изменится в кадре и почему переключение требует пересборки?
4. Треугольник покрыт фрагментами; для каждого считается своя тройка весов. Чему равна интерполированная сумма `w_A + w_B + w_C` в произвольном фрагменте?

::: details Решения и контрольные выводы

1. Середина ребра `A–C`: `w_A = w_C = 0.5`, `w_B = 0` → линейный `(0.5, 0, 0.5)`; sRGB-коды ≈ `(188, 0, 188)`.
2. Мысль неверна. Расстояния от `(0, -0.25)` до вершин: до `A` и `B` ≈ `0.901`, до `C` = `1.0` — не равны. Веса доказываются равенством площадей трёх подтреугольников, и из него следуют веса `1/3`. Равноудалённость от всех вершин — свойство другой точки, центра описанной окружности; у нашего треугольника она не совпадает с центроидом.
3. Кадр вернётся к белому треугольнику [главы «От трёх точек к треугольнику»](../first-triangle/): `select` с константным условием выбирает `SOLID_COLOR`. Константа известна только компилятору шейдеров, поэтому смена значения — пересборка; runtime-переключатели появятся вместе с буферами.
4. Единице: интерполяция линейна, а веса каждого фрагмента — барицентрические с суммой 1.

:::

Цвета вершин пока живут в константах шейдера.
В [следующей главе](../vertex-fetch/) геометрия переедет в буфер: те же байты, но уже данные, которые CPU готовит и загружает.
