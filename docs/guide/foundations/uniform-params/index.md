# Shader bindings и layout: смешанные поля

::: info Только native
Продолжаем [прошлую страницу](../uniform-tint/); меняется состав uniform-структуры.
:::

Один `vec4` — вырожденный случай: размер равен выравниванию, ошибиться негде.
Реальные параметры — смесь векторов и скаляров, и здесь впервые видны и общие правила раскладки WGSL, и дополнительные **ограничения допустимости**, которые uniform-адресное пространство накладывает поверх них.

**Эксперимент:** к `tint` добавляется скалярный `gain`.
При значениях по умолчанию `(tint = 1, gain = 1)` кадр снова обязан совпасть с [«Индексированная геометрия»](../indexed-geometry/); диагностический прогон с `gain = 0.5` проверяет, что умножение происходит в линейных значениях.

## Контракт раскладки

```text
байт:   0          16    20              32
        ├─ tint ────┤─gain─├─── padding ───┤
        │ 4 × f32   │ f32  │ 12 байт пусто │
        └───────────┴──────┴────────────────┘
        ↑ выравнивание 16 → размер 32, хвост добит
```

WGSL-структура и её Rust-аналог:

```wgsl
struct Params {
    tint: vec4<f32>,
    gain: f32,
};
```

```rust
#[derive(ShaderType, Debug, Clone, Copy, PartialEq)]
pub struct Params {
    /// 16 bytes: four f32, size = alignment = 16.
    pub tint: Vec4,
    /// 4 bytes at offset 16; the trailing 12 bytes round the struct size
    /// up to its alignment 16 — the same rule as in any address space.
    pub gain: f32,
}
```

Правила uniform-раскладки для этой структуры:

| Поле | Смещение | Размер | Комментарий |
| --- | --- | --- | --- |
| `tint: vec4<f32>` | 0 | 16 | размер = выравнивание = 16 |
| `gain: f32` | 16 | 4 | начинается сразу после вектора |
| *padding* | 20 | 12 | хвост структуры добивается до её выравнивания — общего правила WGSL, не только uniform. Это не «свободное место» для будущего поля: байты принадлежат раскладке, чтение за пределами полей в шейдере запрещено |
| **структура** | — | **32** | выравнивание структуры = максимум выравниваний полей = 16 |

Правила раскладки WGSL — одни для всех адресных пространств, и звучат они так:

- выравнивание типа `T` (`align`): адрес значения обязан быть кратен ему — `f32`: 4, `vec2<f32>`: 8, `vec3<f32>`: 16, `vec4<f32>`: 16. Матрица выравнивается как её столбец: `mat2x2<f32>` (столбцы `vec2`) — 8, `mat3x3<f32>`/`mat4x4<f32>` (столбцы `vec3`/`vec4`) — 16;
- поле структуры начинается со следующего кратного его выравнивания смещения: `gain` после `vec4` идёт на 16;
- размер структуры округляется вверх до её выравнивания — те самые 12 байтов хвоста из таблицы выше;
- stride массива — размер элемента, округлённый вверх до выравнивания элемента.

Тот же механизм работает и между полями: появись после `gain` ещё и `vec4`, он начался бы на 32 — конец `gain` — 20, следующее кратное 16 — 32.

Откуда же берётся «особость» uniform? Она не в раскладке, а в **ограничениях допустимости**. Uniform-адресное пространство добавляет два требования: stride любого массива кратен 16; поле-структура занимает объём, кратный 16. Нарушение — не «дополнительный паддинг», а ошибка валидации шейдера: `array<f32, 4>` в uniform (естественный stride 4) не будет молча дополнен до 16 — такой тип нельзя положить в uniform. Способы честные: элемент `vec4<f32>`, явная обёртка `@size(16)` или storage-буфер, где плотный `array<f32>` законен. Runtime-массивы (`array<T>` без длины) в uniform запрещены.

Такой же хвостовой padding есть и в storage: эти правила описывают host-shareable типы WGSL — uniform и storage.

А вот на **vertex-записи** эти правила не распространяются. Vertex fetch читает байты по явно заданным с CPU `format`/`offset`/`stride`, никакая WGSL-структура тут раскладку не задаёт: запись `Float32x4 + Float32` может иметь stride 20 без всякого паддинга — тогда как одноимённая WGSL-структура `{ vec4<f32>, f32 }` обязана занимать 32. Плотная 20-байтная запись экономит треть буфера и полностью законна; это два разных контракта — явный (vertex fetch) и выведенный из типа (uniform/storage).

## Сериализация: encase

Байты можно писать и вручную — `cast` вектора, `to_le_bytes` скаляра, нули паддинга, — но это механическая работа, которую стоит автоматизировать.
Крейт **encase** делает ровно это: трейт `ShaderType` описывает WGSL-контракт, `UniformBuffer` пишет байты по правилам выше.

```rust
fn serialize(params: &Params) -> Vec<u8> {
    let mut buffer = UniformBuffer::new(Vec::<u8>::new());
    buffer.write(params).expect("params fit the uniform contract");
    buffer.into_inner()
}
```

`Vec4` — тип четырёх `f32` из библиотеки glam (математика glam появится в своих главах; здесь это обычный тип вектора, который encase умеет раскладывать).
encase не заменяет контракт, а выполняет его: тест в `params.rs` проверяет байты буквально —

```rust
#[test]
fn params_layout_matches_wgsl_uniform_contract() {
    let mut buffer = UniformBuffer::new(Vec::<u8>::new());
    buffer.write(&Params::default()).unwrap();
    let bytes = buffer.into_inner();
    assert_eq!(
        bytes.len(),
        32,
        "uniform struct size rounds up to alignment 16"
    );
    let one = 1.0_f32.to_le_bytes();
    // tint: four f32 at offsets 0, 4, 8, 12; gain: one f32 at offset 16.
    for offset in [0, 4, 8, 12, 16] {
        assert_eq!(&bytes[offset..offset + 4], &one, "field at offset {offset}");
    }
    // The trailing 12 bytes are alignment padding, written as zeros.
    assert!(bytes[20..32].iter().all(|&b| b == 0));
}
```

## Размеры: allocation, binding, layout

Теперь есть три «размера», которые не надо смешивать:

- **allocation** — размер буфера (32 байта);
- **binding** — привязанный диапазон (`min_binding_size` равен размеру структуры, 32);
- **layout-требование** — контракт WGSL (поля с padding'ом).

Буфер может быть больше привязки; привязка — не меньше требования layout'а.
На прошлой странице с одним `vec4` все три числа совпали и составляли 16 — оттого и казалось, что это одно число.

Кадр при умолчательных параметрах совпадает с эталоном [«Индексированная геометрия»](../indexed-geometry/); смена `gain` в проверке меняет каждый пиксель геометрии по линейному закону `encode(0.5 · decode(байт))`.

```sh
cargo run -p uniform-params
cargo test -p uniform-params -p foundations-verify
```

## Проверьте модель

1. Расставьте offsets для структуры `{ a: f32, b: vec4<f32>, c: f32 }` в uniform. Каков её размер?
2. `Params` обходится без `#[repr(C)]` — что encase использует при сериализации вместо Rust-раскладки памяти?
3. `gain = 0`: каким будет кадр? Какой канал это докажет — код или линейное значение?
4. Сколько байтов займёт `array<f32, 4>` в uniform и почему не 16?

::: details Решения и контрольные выводы

1. `a` на 0, `b` на 16 (выравнивание vec4), `c` на 32; размер добивается до 48.
2. `#[derive(ShaderType)]` считает offsets сам: по порядку объявления полей и их выравниванию в WGSL-адресном пространстве, а не по представлению памяти Rust-структуры. `repr(C)` управлял бы раскладкой в памяти Rust, которую encase не читает, — поэтому он здесь и не нужен, и не вреден; контракт задаёт `ShaderType` и проверяется байтами.
3. Геометрия станет чёрной (код 0), фон останется серым 188: `0 · x = 0` в линейных значениях, и кодирование это сохраняет.
4. Вообще нельзя занять: естественный stride такого массива — 4 байта, не кратен 16, и uniform-адресное пространство его запрещает (ошибка валидации, а не авто-паддинг до 16). Честные варианты — элемент `vec4<f32>` (stride 16), обёртка `struct Wrapped { @size(16) v: f32 }` (64 байта на четыре) или плотный `array<f32>` в storage — тема своей главы.

:::
