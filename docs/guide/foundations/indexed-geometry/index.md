# Индексированная геометрия

::: info Только native
Продолжаем через [оболочку](../shell-triangle/); новая сущность одна — index buffer.
:::

Треугольник — ровно три записи. Но прямоугольник из двух треугольников в `TriangleList` — это шесть записей: два угла на общей диагонали входят в оба треугольника, два оставшихся — только в свой.
Индексы позволяют хранить уникальные записи один раз.

**Эксперимент:** треугольник заменяется прямоугольником с углами `(±0.75, ±0.75)` и цветами из главы [«Изображение и числа»](../image-data/): красный, зелёный, синий, белый.
Геометрия — четыре записи и шесть индексов.

## Данные снимка

```rust
const VERTICES: [Vertex; 4] = [
    Vertex {
        position: [-0.75, 0.75, 0.5, 1.0],
        color: [1.0, 0.0, 0.0, 1.0],
    },
    Vertex {
        position: [0.75, 0.75, 0.5, 1.0],
        color: [0.0, 1.0, 0.0, 1.0],
    },
    Vertex {
        position: [-0.75, -0.75, 0.5, 1.0],
        color: [0.0, 0.0, 1.0, 1.0],
    },
    Vertex {
        position: [0.75, -0.75, 0.5, 1.0],
        color: [1.0, 1.0, 1.0, 1.0],
    },
];

// Two triangles over four records, sharing the BL-TR diagonal: indices
// reuse the diagonal corners instead of duplicating records.
const INDICES: [u16; 6] = [0, 1, 2, 2, 1, 3];
```

Запись `Vertex` и её layout — в точности из [прошлой главы](../vertex-fetch/): 32 байта, `Float32x4` на offset 0 и 16.

Треугольники `(0, 1, 2)` и `(2, 1, 3)` делят прямоугольник по диагонали «синий–зелёный»: индексы 1 и 2 входят в оба, запись для них при этом одна.
Обратите внимание на перестановку `(2, 1, 3)`: оба треугольника должны обходиться в одну сторону — так же, как `(0, 1, 2)`. `(1, 2, 3)` обходился бы в противоположную; culling выключен, и сейчас это ни на что не влияет, но при включённом culling один из двух исчез бы.

```text
(0, 1, 2) → записи 0, 1, 2
(2, 1, 3) → записи 2, 1, 3
записи 1 и 2 использованы дважды
```

Считаем полезный объём: четыре записи по 32 байта и шесть `u16` по два — `128 + 12 = 140` байтов против `6 × 32 = 192` у неразделяемых записей.
Это лишь полезные байты: полный расход больше из-за служебных данных и выравниваний, а влияние на скорость требует отдельных измерений.

## Индексный буфер

Индексы — числа, ссылающиеся на записи вершинного буфера данного draw.
Индексный буфер — обычный `Buffer` со своим usage:

```rust
let index_buffer = gpu.device.create_buffer(&BufferDescriptor {
    label: Some("Rectangle indices"),
    size: size_of_val(&INDICES) as u64,
    usage: BufferUsages::INDEX | BufferUsages::COPY_DST,
    mapped_at_creation: false,
});
gpu.queue
    .write_buffer(&index_buffer, 0, bytemuck::cast_slice(&INDICES));
```

Формат `u16` выбирается по числу записей: шести индексам достаточно; `u32` понадобился бы сеткам с миллионами вершин.

## Draw по индексам

```rust
pass.set_pipeline(&self.pipeline);
pass.set_vertex_buffer(0, self.vertex_buffer.slice(..));
pass.set_index_buffer(self.index_buffer.slice(..), IndexFormat::Uint16);
pass.draw_indexed(0..6, 0, 0..1);
```

`draw_indexed(0..6, 0, 0..1)` просит шесть индексов с номерами 0–5.
Для каждого из них GPU читает `u16` из индексного буфера, подставляет его как `vertex_index` в вершинный шейдер — и fetch берёт запись с этим номером: смещение записи равно `vertex_index × stride`.
Шейдер при этом не изменился: `@builtin(vertex_index)` в indexed draw имеет смысл «значение индекса», и вручную читать индексный буфер в шейдере не нужно.

Два оставшихся параметра пригодятся позже, поэтому определим их сейчас:

- **base_vertex** (второй аргумент, у нас `0`) — число, прибавляемое к каждому индексу перед чтением записи; позволяет одному набору треугольников (мешу, mesh) лежать в середине большого буфера.
- **first_vertex** у обычного `draw` — сдвиг диапазона `vertex_index`; у `draw_indexed` аналогичную роль играет начало диапазона индексов.

Ненулевые значения применим, когда появится причина; определение до использования — чтобы следующая встреча не была сюрпризом.

Кадр:

![Эталонный кадр indexed-geometry: прямоугольник с красным, зелёным, синим и белым углами на сером фоне.](/results/indexed-geometry.png)

Цвета по диагонали не совпадают, поэтому градиент «сгибается» вдоль неё: каждый треугольник интерполируется независимо, своим набором барицентрических весов.
Общая гладкость по прямоугольнику — отдельная тема UV-координат из главы о текстурах.

Автоматическая проверка: угловые области кадра обязаны иметь доминирующий канал своего цвета, затем кадр сверяется с эталоном.

```sh
cargo run -p indexed-geometry
cargo test -p foundations-verify
```

## Проверьте модель

1. Выпишите адреса записей (в байтах от начала вершинного буфера) для последовательности индексов `0, 1, 2, 2, 1, 3`.
2. Почему диагональ выбрана «синий–зелёный»? Как изменится кадр при диагонали «красный–белый»?
3. Что произойдёт при индексе `4`? Кто и когда сообщит об ошибке?
4. Напишите индексы для того же прямоугольника в виде двух треугольников с противоположным обходом. Изменится ли кадр в этом снимке и почему?

::: details Решения и контрольные выводы

1. `0, 32, 64, 64, 32, 96` — запись `i` начинается с `i × 32`.
2. При «красный–белой» диагонали сгиб градиента пройдёт из верхнего левого в нижний правый угол; сами цвета углов не изменятся. Диагональ — наш выбор топологии, не свойство прямоугольника.
3. Чтение за пределами буфера с непредсказуемым, но не аварийным результатом (wgpu включает robust buffer access на всех бэкендах) — не паника Rust и не гарантированная ошибка валидации. В учебных данных корректность индексов обеспечивает CPU.
4. Например `[2, 1, 0, 3, 1, 2]`: кадр тот же, потому что culling выключен, а покрытие одинаково.

:::
