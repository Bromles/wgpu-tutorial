# Первый кадр

::: info Только native
Используем winit 0.30, wgpu 30 и pollster 0.4 из workspace репозитория.
Браузера, WASM и учебного framework в этом примере нет: вся программа находится в одном `main.rs`.
:::

Как получить в окне одно сплошное изображение, не рисуя ни треугольников, ни отдельных пикселей?
В главе [«CPU, GPU и очередь»](../cpu-gpu-queue/) мы разделили запись команд, отправку, исполнение и показ.
Теперь каждой операции найдётся конкретный вызов API.

**Эксперимент:** открываем окно с внутренней областью 800×600 физических пикселей и заполняем её линейным RGB `(0.5, 0.5, 0.5)`.
Alpha остаётся равной 1, формат вывода выбираем sRGB согласно контракту главы [«Изображение и числа»](../image-data/#половина-света-не-равна-коду-128).
Массив 2×2 из той главы сюда не загружаем: GPU получает команду очистить всё изображение одним цветом. Эту операцию называют **clear**.

Окно нельзя растягивать мышью; анимации и непрерывного запроса кадров нет.
Цель этого примера — пройти путь до первого кадра с корректной очисткой.
Устойчивое восстановление поверхности и отложенные повторные попытки разбирает глава [«Жизненный цикл поверхности»](../surface-lifecycle/).

## Запускаем снимок

Команду выполняем из корня клонированного репозитория, где находится общий `Cargo.toml`.
Если репозитория ещё нет, сначала клонируйте [Bromles/wgpu-tutorial](https://github.com/Bromles/wgpu-tutorial) и откройте его корень в терминале.
Cargo workspace объединяет пакеты примеров; `-p` выбирает пакет по имени.
Его зависимости и их версии наследуются из корневого манифеста, поэтому копировать один `main.rs` в пустой проект недостаточно.

```sh
cargo run -p first-frame
```

Нужны графический сеанс ОС и работающий драйвер с поддерживаемым native API.
Ожидаемый результат: окно `wgpu | First frame` с однородной серой внутренней областью.
Закрытие окна или Escape завершает программу.

Появление окна зависит от платформы.
В Windows окно показывается сразу — пустым — и простаивает, пока `Context::new` выбирает адаптер и устройство, и лишь затем сереет.
В Wayland композитор не показывает окно, пока не предъявлен первый кадр: окно возникает сразу серым, а инициализация GPU выглядит как пауза между запуском и появлением окна.

Исходник целиком: [`code/guide/foundations/first-frame/src/main.rs` на GitHub](https://github.com/Bromles/wgpu-tutorial/blob/master/code/guide/foundations/first-frame/src/main.rs).
Ниже — короткие фрагменты этого файла рядом с объяснениями; импорты, связующий код и часть обработки ошибок опущены.
Начнём с объектов, которые нужны до первой команды.

## Кто создаёт окно и GPU

**winit** отвечает за окно и сообщения операционной системы: закрытие, клавиатуру, изменение размера, запрос перерисовки.
**wgpu** отвечает за графические ресурсы, команды и связь изображения с выводом в окно.
Окно winit — только цель вывода: устройство wgpu появится ниже, а цвет — после очистки.

**Backend** — реализация wgpu поверх конкретного графического API платформы.
Например, native-приложение может работать через Vulkan, Metal или Direct3D 12.
Код приложения одинаков для всех backend: общий API wgpu скрывает различия платформенных API.

До создания ресурсов понадобятся следующие объекты:

| Объект     | Роль в нашем примере                                                                                     |
| ---------- | -------------------------------------------------------------------------------------------------------- |
| `Instance` | Вход в wgpu: позволяет искать адаптеры и создавать поверхности окон                                      |
| `Adapter`  | Выбранный вариант доступа к GPU через backend и сведения о его поддержке                                 |
| `Device`   | Логическое устройство с согласованными возможностями, через которое создаём ресурсы и записываем команды |
| `Queue`    | Очередь, через которую отправляем команды устройству и передаём кадр на показ                            |
| `Surface`  | Связь wgpu с системой вывода конкретного окна                                                            |

Адаптером бывает и встроенная графика, например в ноутбуках.
Устройство — рабочий интерфейс приложения к выбранному адаптеру.
Поверхность создаём до выбора адаптера, чтобы запросить совместимость именно с этим окном.

`Context` хранит объекты, которые потребуются при перерисовке, и описание будущей настройки поверхности:

```rust
struct Context {
    surface: wgpu::Surface<'static>,
    device: wgpu::Device,
    queue: wgpu::Queue,
    config: wgpu::SurfaceConfiguration,
}
```

Пока это только набор параметров; поверхность настроит вызов `configure` ниже.
Окно передаётся в `create_surface` как владеющий `Arc<Window>`: поверхность может удерживать его, не заимствуя локальную переменную.
Поэтому здесь возможен тип `Surface<'static>`: поверхность освобождается вместе с `Context`.
`Instance` и `Adapter` после настройки не нужны в полях `Context`: созданные объекты удерживают необходимые внутренние связи wgpu.

## Договор с устройством

Возможности GPU различаются, поэтому библиотека требует явно объявить каждый запрос.
В wgpu любой запрос — структура-дескриптор: структуры с суффиксом `Descriptor` описывают параметры создаваемого объекта.
Поля дескриптора определяют, что именно мы просим библиотеку создать.
`InstanceDescriptor::new_without_display_handle()` даёт исходное описание без явно переданного display handle, то есть дескриптора соединения с оконной системой.
Оконную цель ниже передадим отдельно при создании поверхности.

`Backends::PRIMARY` разрешает основные backend-реализации wgpu; название описывает набор API, а выбор видеокарты остаётся за `request_adapter`.
`request_adapter` ищет подходящий адаптер, а `compatible_surface: Some(&surface)` требует возможность вывода на нашу поверхность.
Остальные параметры выбора оставляем стандартными: конкретную модель GPU не фиксируем.

`request_adapter` и `request_device` возвращают future.
**pollster** здесь нужен только для `block_on`: дождаться их результата в синхронном обработчике инициализации.
Здесь `block_on` дожидается создания объектов; кадры после `submit` он не затрагивает.

Начало `Context::new(window: Arc<Window>)`: создаём instance, поверхность и совместимый адаптер.

```rust
let instance = wgpu::Instance::new(wgpu::InstanceDescriptor {
    backends: wgpu::Backends::PRIMARY,
    ..wgpu::InstanceDescriptor::new_without_display_handle()
});
let surface = instance.create_surface(window)?;
let adapter = pollster::block_on(instance.request_adapter(&wgpu::RequestAdapterOptions {
    compatible_surface: Some(&surface),
    ..Default::default()
}))?;
```

### Поддерживается не значит запрошено

**Features** обозначают дополнительные возможности API, **limits** задают численные границы, например максимальную ширину текстуры.
Поддержку адаптера можно узнать через `adapter.features()` и `adapter.limits()`.
При создании `Device` приложение отдельно объявляет, какие возможности ему нужны.
Возможности устройства — это подмножество возможностей адаптера, объявленное в запросе.

Для очистки не нужны дополнительные features, поэтому передаём `Features::empty()`.
`Limits::default()` запрашивает стандартный базовый набор ограничений wgpu.
Если адаптер не удовлетворяет запросу, создание устройства завершится ошибкой.
Размер изображения позже проверяем по `device.limits()`, то есть по договору созданного устройства.

Следующий запрос в `Context::new` возвращает устройство и его очередь:

```rust
let (device, queue) =
    pollster::block_on(adapter.request_device(&wgpu::DeviceDescriptor {
        label: Some("First frame device"),
        required_features: wgpu::Features::empty(),
        required_limits: wgpu::Limits::default(),
        ..Default::default()
    }))?;
```

Отдельно существуют **capabilities поверхности**: какие форматы, режимы показа и способы обработки alpha доступны для пары surface/adapter.
Их возвращает `surface.get_capabilities(&adapter)`.
Features и limits описывают ресурсы устройства, capabilities — вывод изображения в конкретное окно.

### Формат изображения

**Формат текстуры** задаёт каналы, их числовое представление и, для sRGB-вариантов, правило кодирования RGB.
Выбираем первый поддерживаемый формат, для которого `TextureFormat::is_srgb` возвращает `true`.
Если такого нет, завершаем инициализацию с объяснением.

В журнале можно увидеть, например, `Bgra8UnormSrgb` или `Rgba8UnormSrgb`.
`8` — восемь бит на канал, `Unorm` — беззнаковые нормализованные значения.
BGRA и RGBA различаются порядком каналов в представлении.
API принимает именованные компоненты цвета, а выбранный формат определяет их хранение.
В отличие от CPU-массива из главы «Изображение и числа», байты surface-текстуры мы вручную не адресуем.

Суффикс `Srgb` означает, что линейные RGB при записи в эту цель кодируются в sRGB.
Поэтому передаём `0.5`: заранее закодированное `0.735` означало бы двойное кодирование. Ориентир для восьмибитного RGB — примерно 188.
Alpha остаётся линейной и при `a: 1.0` соответствует полному значению канала.

`SurfaceColorSpace::Auto` относится к цветовому пространству вывода поверхности.
Цветовое пространство вывода оставляем обычным (SDR); HDR — тема главы [«HDR и вывод»](../../frame/hdr-output/).
`Auto` оставляет выбор пространства реализации, а кодирование значений по-прежнему задаёт sRGB-формат текстуры — это независимые настройки: представление значений в изображении и договор с системой вывода.

Выбор формата в `Context::new`, после создания устройства:

```rust
let capabilities = surface.get_capabilities(&adapter);
let format = capabilities
    .formats
    .iter()
    .copied()
    .find(wgpu::TextureFormat::is_srgb)
    .ok_or("This example requires an sRGB surface format")?;
```

### Остальные параметры поверхности

`usage: RENDER_ATTACHMENT` разрешает использовать изображения поверхности как цель render pass, то есть участка команд, записывающего результат в прикреплённые изображения.
Такую цель называют **attachment**; ниже у нас будет ровно одно цветовое attachment.
Чтение текстуры поверхности потребовало бы дополнительных usages.

`PresentMode::Fifo` ставит кадры в очередь показа с учётом обновления дисплея.
Такой режим связан с VSync, синхронизацией показа с обновлением экрана, и предотвращает разрыв изображения при смене кадров.
Код проверяет его наличие в `present_modes` и при отсутствии завершается с диагностикой.

`desired_maximum_frame_latency: 2` задаёт желаемую границу числа кадров в очереди вывода.
Механизм presentation воспринимает это значение как подсказку.
`alpha_mode` выбираем первым из поддерживаемых: он определяет, как система вывода трактует alpha поверхности при композиции окна.
При нашем цвете с alpha=1 прозрачности не добиваемся и blending не включаем.

`view_formats: vec![]` означает, что дополнительных форматов для представлений текстур не запрашиваем.
`width: 0` и `height: 0` пока служат **только заполнителями**: этот нулевой размер никогда не передаётся в `surface.configure`.
Настоящий размер узнаем у окна перед первым кадром.

В `Context::new` после выбора `alpha_mode` и проверки поддержки FIFO собираем описание. Эти проверки и запись сведений об адаптере в журнал здесь опущены:

```rust
let config = wgpu::SurfaceConfiguration {
    usage: wgpu::TextureUsages::RENDER_ATTACHMENT,
    format,
    width: 0,
    height: 0,
    present_mode: wgpu::PresentMode::Fifo,
    desired_maximum_frame_latency: 2,
    alpha_mode,
    view_formats: vec![],
    color_space: wgpu::SurfaceColorSpace::Auto,
};
```

### Имена и ошибки

`label: Some("First frame device")` задаёт диагностическое имя объекта.
Метки устройства, view и pass помогают связать сообщения проверки wgpu с нашим кодом; на цвет они не влияют.
**Validation** означает проверку допустимости операций API, например соответствия ресурса заявленному использованию.

Не все GPU-ошибки возвращаются через `Result` именно из вызова, где возникла проблема.
`on_uncaptured_error` устанавливает обработчик ошибок, не перехваченных другим механизмом обработки wgpu.
В этом учебном снимке он пишет сообщение через `tracing::error!` и вызывает `std::process::exit(1)`.
Вызов немедленно завершает процесс без выполнения деструкторов.
Возвращаемые ошибки инициализации приложение обрабатывает отдельно через выход из event loop.

Обработчик устанавливается в `Context::new` сразу после получения устройства:

```rust
device.on_uncaptured_error(Arc::new(|error| {
    tracing::error!(%error, "Unrecoverable GPU error");
    std::process::exit(1);
}));
```

В конце `Context::new` объекты `surface`, `device`, `queue` и описание `config` возвращаются в `Ok(Self { ... })`. Полную инициализацию смотрите в исходнике по ссылке выше.

## Когда окно готово к кадру

**Event loop** принимает события оконной системы и вызывает методы нашего `ApplicationHandler`.
`ActiveEventLoop` предоставляет доступ к операциям цикла внутри этих вызовов: например, созданию окна и запросу выхода.
Обработчик `resumed` сообщает, что приложение может создавать необходимые оконные и графические объекты.
Поэтому окно создаётся там, а не заранее в `main`.

`App` содержит `window`, `context` и `failure`.
Первые два поля сначала равны `None`, последнее хранит причину нештатного завершения для возврата из `main`.
В `resumed` уже существующий context предотвращает повторную инициализацию.
Если окна ещё нет, создаём его с заголовком, `PhysicalSize::new(800, 600)` и `with_resizable(false)`, затем создаём `Context`.

**Физический размер** измеряется в пикселях внутренней области окна, без рамки и заголовка.
Оконная система переводит логический размер в физические пиксели через масштабный коэффициент; на плотных дисплеях он больше единицы.
Мы запрашиваем физические 800×600, но для настройки поверхности всё равно читаем фактический `window.inner_size()`: оконная система распоряжается размером сама.

`window.request_redraw()` запрашивает событие `WindowEvent::RedrawRequested` вместо немедленной отрисовки.
В обработчике этого события сначала проверяем размер: при нулевой ширине или высоте кадр пропускаем.
Нулевой размер может появиться из-за состояния окна; текстуру нулевого размера для вывода не настраиваем.

Метод `Context::resize` дополнительно проверяет размер и сравнивает его с `max_texture_dimension_2d` устройства.
При превышении лимита возвращает ошибку; при изменении размера обновляет config и вызывает `surface.configure(&device, &config)`.
**Configure** применяет описание к поверхности, подготавливая её к выдаче изображений нужного размера и формата.
При первом ненулевом размере сравнение с заполнителями `(0, 0)` обеспечивает первую настройку.

`resize` вызывается **до получения изображения кадра**; перенастройку не совмещаем с живым surface frame.
Название `resize` охватывает и начальную настройку; полноценное интерактивное изменение размера разбирает следующая глава.

События `Resized(_)` и `Occluded(false)` только запрашивают redraw; последнее сообщает, что окно больше не скрыто от показа.
Закрытие окна и нажатие физической клавиши Escape вызывают `event_loop.exit()`.
События чужого `WindowId` игнорируются, а redraw без context ничего не делает.
`suspended` освобождает context; при следующем `resumed` его можно создать заново для сохранённого окна.
Полную политику восстановления разбирает глава «Жизненный цикл поверхности».

Ветка `WindowEvent::RedrawRequested` внутри `App::window_event` связывает проверку размера, настройку и кадр. Остальные ветки описаны выше и приведены в полном исходнике:

```rust
WindowEvent::RedrawRequested => {
    let Some(context) = &mut self.context else {
        return;
    };
    let size = window.inner_size();
    if size.width == 0 || size.height == 0 {
        return;
    }
    // No surface texture exists while resize configures the surface.
    if let Err(error) = context.resize(size).and_then(|()| context.render(window)) {
        tracing::error!(%error, "Rendering stopped");
        self.failure = Some(error.to_string());
        event_loop.exit();
    }
}
```

## Surface, frame и view

Поверхность живёт между кадрами; изображение для записи она выдаёт по запросу.
`surface.get_current_texture()` получает доступное изображение для очередного вывода: это шаг **acquire**.
Возвращаемый frame содержит `texture`, в которую запишем цвет, и связан с последующей передачей на показ.
Каждый кадр начинается с нового получения.

**Texture view** представляет выбранную текстуру или её часть с определённым форматом для использования в командах.
`frame.texture.create_view(...)` здесь создаёт стандартное представление изображения кадра, добавляя только диагностическое имя.
Именно ссылку на view передаём в цветовое attachment, а сам frame затем отдаём `queue.present`.

В wgpu 30 получение возвращает `CurrentSurfaceTexture`; до кода разберём все его исходы в нашем снимке:

| Исход               | Решение в этом примере                                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| `Success(frame)`    | Очистить и передать этот frame на показ                                                                                   |
| `Suboptimal(frame)` | Сделать то же самое, без перенастройки и изменения пути показа                                                            |
| `Occluded`          | Пропустить кадр с `Ok(())`, не отправлять команды и не делать present                                                     |
| `Timeout`           | Вернуть ошибку с советом перезапустить этот пример или перейти к отложенным попыткам в главе «Жизненный цикл поверхности» |
| `Outdated`, `Lost`  | Вернуть ошибку о необходимости восстановления поверхности                                                                 |
| `Validation`        | Вернуть ошибку и обратиться к GPU-диагностике                                                                             |

`Suboptimal` означает, что изображение ещё пригодно, хотя состояние вывода уже не оптимально.
`Outdated` указывает на устаревшую настройку поверхности, `Lost` на потерю поверхности, а `Timeout` на истечение ожидания доступного изображения.
В этом примере `Outdated`, `Lost` и `Timeout` намеренно останавливают приложение.
`window_event` записывает ошибку как `Rendering stopped`, сохраняет `failure` и запрашивает выход.
Здесь нет ни таймера повторной попытки, ни автоматической перенастройки после ошибки acquire.

В `Context::render` после разбора результата acquire создаём view полученного `frame`. Сам `match` с перечисленными исходами здесь опущен:

```rust
let view = frame.texture.create_view(&wgpu::TextureViewDescriptor {
    label: Some("First frame surface view"),
    ..Default::default()
});
```

## Записываем очистку

`Device::create_command_encoder` создаёт **encoder**, объект записи команд на CPU.
`begin_render_pass` открывает render pass с заданными attachment и правилами обращения с их содержимым.
Pass ещё не отправляет работу GPU: он записывает её в encoder.

`color_attachments` содержит одну цель `Some(...)`, чей `view` указывает на изображение кадра.
Поле `ops` задаёт две независимые границы работы с содержимым:

- `LoadOp::Clear(color)` задаёт начальное заполнение attachment указанным цветом. Альтернатива `LoadOp::Load` сохраняет прежнее содержимое для дальнейшей работы.
- `StoreOp::Store` требует сохранить результат после pass. `StoreOp::Discard` разрешает не сохранять его; для показа нужен `Store`.

**Clear** — операция над attachment: геометрия и вызов `draw` для неё не нужны.
**Шейдер** — программа GPU для вычисления результатов рисования или другой работы; своего шейдера для этой очистки мы не пишем.
Не нужен и render pipeline, набор настроек выполнения рисования с шейдерами.

`resolve_target: None` означает отсутствие дополнительной цели для результата MSAA, сглаживания с несколькими выборками на пиксель.
В нашем кадре одна выборка; механизм MSAA и resolve здесь не используется и будет введён отдельно.
`depth_slice: None` — цель представляет обычное двумерное изображение.

Оставшиеся стандартные поля `RenderPassDescriptor` задают значения по умолчанию: без depth/stencil attachment, то есть изображения для данных глубины и маски, и без запросов измерений.
У нас один pass, одно цветовое attachment, без MSAA и blending.

Продолжение `Context::render`: создаём encoder и записываем один pass. Это весь блок записи очистки, без получения frame и отправки команд:

```rust
let mut encoder = self
    .device
    .create_command_encoder(&wgpu::CommandEncoderDescriptor {
        label: Some("First frame clear encoder"),
    });
{
    let _pass = encoder.begin_render_pass(&wgpu::RenderPassDescriptor {
        label: Some("First frame clear pass"),
        color_attachments: &[Some(wgpu::RenderPassColorAttachment {
            view: &view,
            resolve_target: None,
            ops: wgpu::Operations {
                load: wgpu::LoadOp::Clear(wgpu::Color {
                    r: 0.5,
                    g: 0.5,
                    b: 0.5,
                    a: 1.0,
                }),
                store: wgpu::StoreOp::Store,
            },
            depth_slice: None,
        })],
        ..Default::default()
    });
}
```

Вложенный блок ограничивает время жизни `_pass`: при выходе pass заканчивает запись и освобождает encoder для дальнейших действий.
`encoder.finish()` завершает запись и возвращает **command buffer**, готовый пакет команд.
Содержимое кадра появится при исполнении команд на GPU.
`queue.submit([encoder.finish()])` отправляет этот пакет устройству без обязательного ожидания завершения GPU.

Перед показом `window.pre_present_notify()` уведомляет winit о предстоящем present для согласования с оконной системой.
Затем **в используемой версии wgpu 30** вызываем `queue.present(frame)`, а не `frame.present()` из старых примеров.
Как обсуждалось в главе [«CPU, GPU и очередь»](../cpu-gpu-queue/), present передаёт кадр системе вывода и не служит сигналом завершения GPU; CPU-ожидание после каждого submit не добавляем.

Сразу после блока pass в `Context::render` выполняем отправку и передачу на показ. Запись в журнал и `Ok(())` после этого блока опущены:

```rust
self.queue.submit([encoder.finish()]);
window.pre_present_notify();
self.queue.present(frame);
```

## От main до результата

`tracing_subscriber` устанавливает вывод диагностических сообщений уровня INFO и более серьёзных.
`EventLoop::new()` создаёт цикл событий, а `run_app(&mut app)` передаёт ему наш обработчик до завершения работы.
Именно цикл вызывает описанные выше `resumed` и `window_event`; явного `loop { render() }` здесь нет.
После выхода сохранённая `failure` превращается в ошибочный результат `main`, чтобы нештатная остановка не выглядела успешной.

Точка входа короткая, поэтому её приводим целиком:

```rust
fn main() -> Result<(), Box<dyn Error>> {
    tracing_subscriber::fmt()
        .with_max_level(tracing::Level::INFO)
        .init();
    let event_loop = EventLoop::new()?;
    let mut app = App::default();
    event_loop.run_app(&mut app)?;
    if let Some(error) = app.failure {
        return Err(error.into());
    }
    Ok(())
}
```

При успешном проходе в журнале ожидаются `Selected GPU` с именем адаптера, backend и форматом, `Configured surface` с фактическим размером и `Rendered clear`.
Последнее сообщение означает, что команды отправлены и кадр передан на показ.
Если инициализация не удалась, сначала смотрите `Initialization failed` и конкретную причину: нет подходящего адаптера, sRGB-формата или нужной поддержки.
При ошибке validation используйте также метки `First frame ...`, чтобы найти соответствующий объект в исходнике.

Успешный путь теперь можно прочитать без скрытого шага:
ненулевой размер → configure при необходимости → acquire → view → clear/store → submit → present.
Следующий кадр возникает по событию redraw.
Одного кадра достаточно для неподвижного фона; при последующих перерисовках выполняется та же очистка.

## Проверьте модель

1. Какой восьмибитный sRGB-код ожидается от линейных RGB `(0.5, 0.5, 0.5)`? Почему не 128?
2. Измените только `r` в `LoadOp::Clear` на `1.0`, сохранив `g = b = 0.5` и `a = 1.0`, затем перезапустите пример. Каким станет цвет и каковы ожидаемые коды RGB?
3. Почему нельзя заменить `Store` на `Discard`, если после pass мы всё равно вызываем present? Нужно ли добавлять шейдер, чтобы вернуть серый фон?
4. Что произойдёт при нулевом размере, `Occluded` и `Timeout`? Где находится повторная попытка после timeout?

::: details Решения и контрольные выводы

1. Примерно `(188, 188, 188)`: линейные 0.5 кодируются в sRGB примерно как 0.735, затем квантуются в восемь бит. 128 получается от простого масштабирования 0.5 без sRGB-кодирования.
2. Получится светлый красный оттенок с ожидаемыми RGB около `(255, 188, 188)`. Меняется весь фон, не один пиксель; даже при формате BGRA изменять нужно поле `r`, а не `b`.
3. `Discard` не требует сохранить содержимое для последующего показа. Нужен `Store`; для возвращения серого достаточно снова задать `r: 0.5`, шейдер не требуется.
4. Нулевой размер пропускается до configure и acquire. `Occluded` пропускает кадр без получения изображения и без present. `Timeout` возвращает диагностическую ошибку и приводит к выходу; повторной попытки в этом примере нет.

:::

Числа 188 и 255 здесь — предсказание цветового контракта, проверяемое эталонным кадром.
Внешний вид зависит от системы вывода и дисплея, поэтому оценка серого на глаз не проверяет точность кодирования.
Для этой главы достаточно связать настройку поверхности, запись очистки и показ с конкретными объектами API.
В главе [«Жизненный цикл поверхности»](../surface-lifecycle/) сохраним тот же цвет, но расширим поведение при изменении размера, недоступности и потере поверхности.
