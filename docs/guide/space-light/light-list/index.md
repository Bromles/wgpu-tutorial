# Список и сумма источников

::: info Только native
Снимок [«Точечный источник и конус»](../light-point/): сцена и формулы прежние; uniform одного источника заменён массивом в storage-буфере, клавиша `L`.
:::

Настоящая сцена редко освещена одним источником.
Свет аддитивен: вклады источников складываются, и для этого достаточно… сложить.
Интересна не формула суммы, а данные: как хранить «сколько угодно» источников и как шейдер узнаёт, сколько их сейчас.

**Эксперимент:** та же плоскость и камера, пул из трёх статичных источников: два одинаковых над центром `(0, 0, 1)` с мощностью `0.4` и один в `(1.4, 0, 1)`.
Клавиша `L` циклически включает `1 → 2 → 3` источника; `ambient = 0`, `albedo = 0.5`.

## Пул в read-only storage

Один источник — один uniform; много источников — **массив**, и его место в `var<storage, read>`: массивы нефиксированной длины в uniform-адресном пространстве запрещены правилами WGSL.
Запись пакуем в два `vec4` — свободные четвёртые компоненты (их вводила [глава о материале и блике](../blinn-phong/)) несут службу: `pos.w` — мощность, `spot.xyz` — ось конуса, `spot.w` — флаг прожектора (здесь у всех 0: чистые точки).

```rust
#[derive(ShaderType, Debug, Clone, Copy, PartialEq)]
pub struct Light {
    pub pos: Vec4,
    pub spot: Vec4,
}
```

```rust
pub const LIGHTS: [Light; MAX_LIGHTS] = [
    Light {
        pos: Vec4::new(0.0, 0.0, 1.0, 0.4),
        spot: Vec4::new(0.0, 0.0, -1.0, 0.0),
    },
    Light {
        pos: Vec4::new(0.0, 0.0, 1.0, 0.4),
        spot: Vec4::new(0.0, 0.0, -1.0, 0.0),
    },
    Light {
        pos: Vec4::new(1.4, 0.0, 1.0, 0.4),
        spot: Vec4::new(0.0, 0.0, -1.0, 0.0),
    },
];
```

Два одинаковых источника над центром — их вклады сложатся, и мы это проверим; третий стоит отдельно.
Два `vec4` — ровно 32 байта, шаг массива кратен 16 без всякого паддинга — раскладка [«Смешанные поля»](../../foundations/uniform-params/) в полном блеске.

Возможности проверяем до использования: read-only storage во фрагментной стадии WebGPU поддерживает всегда, а лимиты устройства (`max_storage_buffers_per_shader_stage` — 8 по умолчанию, `max_storage_buffer_binding_size` — 128 МиБ) с запасом покрывают наш пул из 96 байт: даже по 16 байт на источник в 128 МиБ помещаются миллионы записей.

## Сколько источников? for с границей из uniform

Количество активных источников — свойство кадра, оно едет в uniform рядом с камерой.
Число храним как `f32`: один скаляр после `mat4x4` encase сам дополнит до 80 байт структуры, без ручного паддинга (подошёл бы и `u32` — выбор ради однородности скалярных полей); в шейдере явно приводим его к целому через `u32(count)`.

Сам WGSL-цикл:

```wgsl
    var sum = 0.0;
    // for = init; condition; continuing. The bound comes from the uniform,
    // so only the first `count` records of the pool are ever read.
    for (var i = 0u; i < u32(params.count); i++) {
        sum += contribution(lights[i], input.world_position, n);
    }
```

У `for` в WGSL заголовок — `инициализация; условие; продолжение`: `var i = 0u` выполняется один раз, `i < bound` проверяется перед каждой итерацией (включая первую), `i++` — после тела.
Формула одного вклада не изменилась — она переехала в функцию `contribution`, и цикл лишь складывает результаты.

## Границы

Массив в привязке имеет длину `размер привязки / шаг = 96 / 32 = 3`, а цикл читает только записи `0..count`.
Безопасность даёт само условие: `i < count` при `count ≤ 3` не выпускает индекс за пределы пула, а CPU-сторона клампит счётчик (`set_count`, `% MAX_LIGHTS` в обработчике клавиши).
Выход за границу runtime-массива в WGSL — не «ноль», а ошибка шейдера; границу мы держим сами.

## Сумма линейных вкладов

Свет складывается в линейных величинах — до какого-либо кодирования:

```text
один источник:  0.2 линейных → код 124
два одинаковых: 0.4 линейных → код 170        не 248!
```

Удвоение света — удвоение линейного значения; sRGB-код растёт медленнее (помните [кривую кодирования](../../foundations/srgb-mixing/)) — и это ещё один повод суммировать до кодирования, а не после.
`count = 0` оставляет только ambient: цикл не выполняется ни разу, и в нашей главе (ambient 0) кадр под пулом источников чёрный.
Ambient прибавляется **один раз, после цикла** — это свойство сцены, а не источника; внутри цикла он рос бы вместе со счётчиком.

## Снимок

```wgsl
struct Light {
    pos: vec4<f32>,
    spot: vec4<f32>,
};

// Matches the encase layout: the matrix first, then the count scalar
// padded to the 16-byte struct tail; 80 bytes in total.
struct Params {
    view_proj: mat4x4<f32>,
    count: f32,
};

@group(0) @binding(0) var<uniform> params: Params;
@group(0) @binding(1) var<storage, read> lights: array<Light>;
```

Storage-буфер пишется один раз при создании — пул статичен; каждый кадр обновляется только маленький uniform с камерой и счётчиком.
Проверка сверяет центр кадра с CPU-моделью суммы для `count = 1, 2, 3` (коды `124`, `170`, `177`), фиксирует нелинейность кодов (`170 < 2·124`) и `count = 0` → чёрный.

![Кадры light-list: один источник против трёх на одной плоскости.](/results/light-list-counts.png)

Слева `count = 1`, справа `count = 3`: два одинаковых источника над центром складывают вклады, третий в стороне добавляет свой. Вклады суммируются в линейном свете — яркость растёт с числом источников, а коды растут медленнее (`124 → 170 → 177`).


## Проверьте модель

1. Два одинаковых источника дают линейные `0.4` и код `170`. Какое линейное значение и код вы ждёте от четырёх таких же (если расширить пул)?
2. Почему `count` едет как `f32`, а сравнение в цикле — с `u32(params.count)`?
3. Что изменится в кадре, если ambient занести внутрь цикла?
4. Почему цикл не может прочитать запись за пределами пула, даже если `count` по ошибке окажется больше 3?

::: details Решения и контрольные выводы

1. Линейно — `0.8`; код — `encode(0.8)·255 ≈ 231`, меньше 255: линейная сумма растёт вдвое, код — по кривой sRGB.
2. За матрицей нужен один скаляр — подошёл бы и `u32`: до 80 байт структура добиралась бы так же; `f32` выбран для однородности скалярных полей. Индекс и счётчик цикла — целые, поэтому сравнение ведём в `u32`: типы в условии должны совпадать.
3. Ambient прибавлялся бы `count` раз: кадр с нулём источников остался бы без него, а с тремя — получил бы тройной. Он один на сцену — поэтому после цикла.
4. Ошибку не допускает дисциплина данных: CPU клампит `count` до длины пула (`set_count`, `% MAX_LIGHTS`), и условие `i < count` держит индексы в границах. Сам WGSL за пределами runtime-массива ошибку не прощает — это контракт CPU-стороны.

:::

Источники складываются, поверхности пока непрозрачны.
