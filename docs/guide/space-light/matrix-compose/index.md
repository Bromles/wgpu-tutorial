# Матрицы и композиция

::: info Только native
Тот же асимметричный треугольник; `M` переключает порядок преобразований.
:::

«Масштаб, потом поворот, потом перенос» — три пары формул, которые нельзя перепутать.
Матрица упаковывает всю цепочку в один объект: одна структура данных, одно умножение в шейдере, любой порядок — явный.

**Эксперимент:** фиксированы масштаб `1`, угол `π/2` и перенос `(0.25, 0)`; клавиша `M` меняет только порядок: `T·R` против `R·T`.
Кадры разные — и это главный факт главы.

## Базис и образы осей

Вывод [прошлой главы](../triangle-motion/) переформулируем: поворот задаётся тем, куда попадают базисные направления.
Расположим образы осей **столбцами** таблицы — это и есть матрица:

```text
R(θ) = | cos θ  −sin θ |      T(t) = | 1  0  tx |
       | sin θ   cos θ |             | 0  1  ty |
       «матрица» поворота             перенос стал матрицей
```

Матрица — это запись линейного преобразования: её столбцы — образы базисных векторов, а умножение `M·p` собирает точку из компонентов по этим образам:

```text
M · p = x · (столбец 1) + y · (столбец 2) + ...
```

Поворот и масштаб — линейные: `M·(a + b) = M·a + M·b`, образ суммы равен сумме образов.
Перенос линеен только при `t = 0` — и потому «плоской» матрицей 2×2 не выражается: линейное преобразование всегда оставляет начало координат на месте (`M·(0,0) = (0,0)`); ненулевой перенос сдвигает и его.

## Однородные координаты: w = 1 и w = 0

Добавим четвёртую компоненту и перенесём её в столбец:

```text
         | 1 0 0 tx |              точка:  (x, y, z, 1)
T·p =    | 0 1 0 ty | · p          направление: (x, y, z, 0)
         | 0 0 1 tz |
         | 0 0 0 1  |
```

У точки `w = 1`: столбец переноса добавляется целиком — точка едет.
У направления `w = 0`: столбец переноса умножается на ноль — направление не меняется.
Матрица сама различает типы, которые мы в [главе «Точки и движение»](../triangle-motion/) различали вручную.

## Композиция: порядок действий

Произведение матриц — композиция: `(A·B)·p = A·(B·p)`.
Действие читается **справа налево**: в `T·R·p` сначала поворот, потом перенос.

Для переноса `(0.25, 0)` и поворота `π/2`:

```text
T·R · (0,0):  R даёт (0,0), T добавляет (0.25, 0)  →  (0.25, 0)
R·T · (0,0):  T даёт (0.25, 0), R поворачивает     →  (0, 0.25)
```

Одни и те же матрицы, разный порядок — разные миры.
Матричное умножение некоммутативно, и это не неприятность, а смысл: порядок операций закодирован в порядке множителей.

![Кадры matrix-compose: слева композиция T·R, справа R·T — один и тот же треугольник в разных позах.](/results/matrix-compose-tr-rt.png)

Слева — `T·R` (CPU собирает `translate * rotate`): повёрнутый треугольник целиком уезжает вправо. Справа — `R·T`: поворот вращает уже смещённые вершины вокруг начала координат и уводит треугольник вверх. Смотрите на разницу поз при одной и той же паре операций.

## Снимок

Весь преобразователь — один uniform на 64 байта:

```wgsl
// Column-major mat4x4; multiplication acts right-to-left on the vector.
@group(0) @binding(0) var<uniform> transform: mat4x4<f32>;

@vertex
fn vs_main(input: VertexInput) -> VertexOutput {
    var output: VertexOutput;
    output.position = transform * vec4<f32>(input.position.xy, 0.5, 1.0);
    output.color = input.color.rgb;
    return output;
}
```

CPU собирает композицию конструкторами glam — после ручного вывода выше:

```rust
fn transform(order: Order) -> glam::Mat4 {
    let translate = glam::Mat4::from_translation(glam::Vec3::new(0.25, 0.0, 0.0));
    let rotate = glam::Mat4::from_rotation_z(std::f32::consts::FRAC_PI_2);
    match order {
        Order::TranslateRotate => translate * rotate,
        Order::RotateTranslate => rotate * translate,
    }
}
```

**Хранение отдельно от математики.** Мы записываем преобразование построчно; в памяти glam хранит матрицу по столбцам (внутри — `Mat4::from_cols`, наружу — побайтовая сериализация), и WGSL `mat4x4` принимает ровно эти 16 `f32`: encase сериализует `Mat4` в 64 байта — знакомый контракт [«Смешанные поля»](../../foundations/uniform-params/) сработал и тут.
«Строки в учебнике, столбцы в памяти» — не противоречие, а два уровня записи одного объекта.

Проверка: для обоих порядков кадр сверяется с CPU-композицией той же матрицы (по внутренним пикселям, как в [главе «Точки и движение»](../triangle-motion/)).

```sh
cargo run -p matrix-compose
cargo test -p foundations-verify
```

## Проверьте модель

1. Вычислите `T·R·(1, 0)` и `R·T·(1, 0)` для наших матриц. Почему ответы разные?
2. Почему перенос направления `(0.5, 0, 0, 0)` матрицей `T` не меняет его?
3. Сколько байтов занимает uniform и почему граница привязки — 64?
4. Запишите матрицу масштаба `S(2)` и проверьте: `S·R` и `R·S` при нашем угле совпадают или нет?

::: details Решения и контрольные выводы

1. `T·R`: поворот даёт `(0, 1)`, перенос — `(0.25, 1)`. `R·T`: перенос даёт `(1.25, 0)`, поворот — `(0, 1.25)`.
2. Четвёртая компонента `w = 0` обнуляет вклад столбца переноса; перенос добавляется только точкам.
3. `16 f32 × 4 = 64` байта; alignment матрицы 16 — размер кратен ему без padding.
4. `S = diag(2, 2, 1)`; `S·R = R·S` здесь совпадают, потому что масштаб равномерный: поворот коммутирует с растяжением по всем осям одинаково. Неравномерный масштаб порядок уже чувствует — увидим в главе о нормалях.

:::
