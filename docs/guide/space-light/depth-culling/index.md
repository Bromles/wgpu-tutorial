# Ориентация и видимость

::: info Только native
Камера и проекция — из [«Проекция и путь на экран»](../ortho-perspective/). Сцена — два пересекающихся треугольника; клавиши `C`, `D`, `O`, `F`.
:::

До сих пор видимость определял порядок draw: «художник» из [«Проекция и путь на экран»](../ortho-perspective/) рисовал из глубины, и это работало, пока объекты не пересекаются.
Поставим два треугольника **накрест** — и спросим: почему порядок всё-таки не должен решать, кто ближе?

**Эксперимент:** красный треугольник в плоскости `z = 0`, синий — в наклонной, пересекаются по вертикальной линии `x = 0, z = 0`. Плоскость `x = 0` содержит глаз камеры `(0, 0, 5)` и спроецировалась бы в линию — наклон разворачивает её к камере. Начальное состояние: culling выключен, depth включён, рисуется красный затем синий. `C` перебирает режимы culling, `D` выключает depth, `O` меняет порядок draw, `F` переворачивает winding синего (перестановкой двух индексов).

## Обход вершин и culling

У замкнутой непрозрачной поверхности задние грани не видны никогда — но растеризатор всё равно тратит на них фрагменты. Ориентация обхода позволяет выбросить такие треугольники до фрагментации.

Треугольник имеет ориентацию на экране: **winding** — направление обхода вершин (по часовой или против). `FrontFace::Ccw` объявляет «против часовой — лицевая сторона»; `cull_mode` решает, что выбрасывать: `None`, `Some(Face::Front)` или `Some(Face::Back)`.

```text
экран (ось NDC +Y вверх)    cull Front:
      2                     красный: 0→1→2 = CCW — лицевой,
     ╱ ╲                    выброшен
    ╱   ╲
  0 ───── 1                 синий: 3→4→5 = CCW — лицевой,
                            тоже выброшен. Кадр пуст.
      5
     ╱ ╲                    Что изменит FLIPPED:
    ╱   ╲                   синий станет 5→4→3 = CW —
  3 ───── 4                 заднегранный, выживет один.
```

У нашей сцены оба треугольника обойдены против часовой стрелки от камеры — оба «лицевые». Поменять это можно двумя индексами:

```rust
/// Two triangles through six indices. Swapping the outer indices of the
/// blue triple reverses its winding: nothing changes until culling is on,
/// then the triangle turns from front-facing into back-facing.
const INDICES: [u16; 6] = [0, 1, 2, 3, 4, 5];
const FLIPPED_INDICES: [u16; 6] = [0, 1, 2, 5, 4, 3];
```

Геометрия та же, но при `cull Front` кадр из пустого становится «только синий».

## Depth attachment: договор трёх чисел

Второй механизм — **depth-буфер**: текстура `Depth32Float` размером с кадр; в каждом её текселе — глубина ближайшего фрагмента. Из [«Clip, экран и интерполяция»](../clip-viewport/) мы знаем её содержимое: нелинейная глубина, 0 — ближе всего, 1 — far-плоскость. Три настройки обязаны быть согласованы:

- **clear = 1.0** — «дальше всего»: стартовая стена, которую пробивает любой фрагмент;
- **compare = Less** — фрагмент проходит, если он ближе записанного;
- **write = on** — прошедший фрагмент записывает свою глубину следующим соперникам.

Attachment — ресурс сэмпла, а не фреймворка: размер приходит контрактом `resize` ещё до первого кадра, поэтому текстура пересоздаётся в `draw` по `pending_size`, как аспект в главах о проекции и clip.

```rust
            // The attachment is cleared to 1.0: with `Less` this is the
            // "farther than everything" wall. Pipelines without depth
            // simply ignore it.
            depth_stencil_attachment: Some(RenderPassDepthStencilAttachment {
                view: self
                    .depth_view
                    .as_ref()
                    .expect("depth exists after recreate"),
                depth_ops: Some(Operations {
                    load: LoadOp::Clear(1.0),
                    store: StoreOp::Store,
                }),
                stencil_ops: None,
            }),
```

pipeline без depth-теста просто игнорирует attachment — поэтому `D` переключает вариант pipeline, а не структуру прохода.

## Настройки живут в pipeline

И culling, и depth — состояние pipeline, а не прохода. Полный переключатель — 3 culling × 2 depth = 6 вариантов pipeline, построенных одной функцией:

```rust
            // The pass always has a depth attachment, so even the
            // "depth off" pipeline must declare the format: it simply never
            // rejects (Always) and never writes.
            depth_stencil: Some(DepthStencilState {
                format: TextureFormat::Depth32Float,
                depth_write_enabled: Some(depth),
                depth_compare: Some(if depth {
                    CompareFunction::Less
                } else {
                    CompareFunction::Always
                }),
                stencil: Default::default(),
                bias: Default::default(),
            }),
```

И финальный акт: два draw в любом порядке — с depth порядок перестаёт иметь значение.

```rust
        // With the depth test on, both orders must produce the same frame;
        // with it off, the last draw wins wherever both triangles cover.
        let (red, blue) = (0..3u32, 3..6);
        match self.order {
            Order::RedFirst => {
                pass.draw_indexed(red, 0, 0..1);
                pass.draw_indexed(blue, 0, 0..1);
            }
            Order::BlueFirst => {
                pass.draw_indexed(blue, 0, 0..1);
                pass.draw_indexed(red, 0, 0..1);
            }
        }
```

Вершины синего связывают `x` и `z` одним знаком: правая по экрану половина придвинута к глазу, левая — отодвинута, поэтому слева от линии пересечения (экранной вертикали по центру) ближе красный, справа — синий. При включённом depth оба порядка дают **один и тот же кадр**. Выключите `D` — и у пересечения начнёт побеждать последний draw.

![Кадры depth-culling: одна и та же пара треугольников — слева depth-тест включён, справа выключен.](/results/depth-culling-order.png)

Одна и та же пара треугольников в одном порядке draw (`RedFirst`): слева depth включён — виден ближайший. Справа depth выключен — в зоне перекрытия побеждает последняя нарисованная команда.

## Точность и z-fighting

Гипербола из [главы о clip и интерполяции](../clip-viewport/) имеет цену: у near-плоскости глубина меняется быстро, у far — еле-еле. Далёкие поверхности получают почти одинаковые значения глубины, и при точном совпадении сравнение `Less` отклоняет нового — остаётся **первый записанный** фрагмент. Две почти совпадающие плоскости мерцают в зависимости от порядка и ракурса — это z-fighting; лекарство — раздвинуть поверхности или сузить диапазон near/far. Reverse-Z пока не вводим: обычный Z с `clear = 1`, `Less`, `write` — договор этой главы.

Автоматическая проверка гоняет кадр в обоих порядках и сравнивает кадры попиксельно, допуская единичные различия на самой линии пересечения (там две поверхности делят глубину), пробует зонды по обе её стороны и проверяет, что перестановка индексов при `cull Front` возвращает в кадр ровно один треугольник.

```sh
cargo run -p depth-culling
cargo test -p foundations-verify --test depth_culling
```

## Проверьте модель

1. Почему clear-значение именно 1.0, а не 0.0?
2. Два фрагмента с побитово равной глубиной. Который из них пройдёт `Less` — и какой останется видимым?
3. `C` дошёл до `Front`: что осталось в кадре? А после нажатия `F` (переворота winding синего)?
4. `D` выключил depth. Что происходит с цветом у линии пересечения при нажатии `O`?

::: details Решения и контрольные выводы

1. `Less` пропускает только строго меньшее: 1.0 — «дальше всего», стартовая стена. Clear 0.0 закрыл бы кадр — ни один фрагмент не прошёл бы `depth < 0`.
2. Пройдёт только первый записанный: против clear-стены 1.0 он проходит, а второму его же глубина даёт «не меньше» — отбрасывается. Видимым остаётся первый записанный; порядок draw всплывает ровно в этой точке — ещё одна причина избегать совпадающих глубин.
3. Пустой кадр: оба треугольника обходимы против часовой (front), `Front` отсекает лицевые. После перестановки синий становится back-facing и выживает один.
4. Виден последний нарисованный: там, где оба покрывают пиксель, победителя назначает порядок. Именно это depth-буфер убирает: с ним ближайшая поверхность выигрывает в любом порядке.

:::

Видимость больше не зависит от порядка — можно отдать камеру игроку.
