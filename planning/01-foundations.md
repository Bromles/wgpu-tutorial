# Паспорта 01–14: основы и данные

Этап 2 по REWRITE_PLAN.md и KNOWLEDGE_MAP.md; [родительский индекс паспортов](../CHAPTER_PASSPORTS.md). Это учебные границы и критерии будущей приёмки, не статьи, реализация или отчёт о прогонах. Имена локальных файлов обозначают роли внутри самостоятельных снимков, не новую структуру репозитория.

Снимки сохраняют предыдущие настройки, если изменение не названо явно. После 04: clip-позиции с w=1, непрозрачный вывод, без depth/culling/blending, один sample; без камеры, матриц и GUI. Подписи принадлежат схемам, не требуют шрифтов в приложении. Переключатели и сброс локальны снимку: сначала константы, после объяснения событий winit допустимы клавиши; будущий input framework не используется. Оболочка 05 является общей неизменяемой минимальной crate (ролевое имя `shell`), не растущими локальными копиями; содержит только введённые lifecycle/configuration и прямую передачу известных событий. Разделённые страницы идут последовательно внутри базового ID, контрольная точка не добавляет внешних prerequisites.

## 01. Изображение и числа

- **Вопрос/вход:** Входных ID нет, достаточно Rust и арифметики. Как числа становятся изображением? Сетка → пиксель → координаты строки/столбца → RGB и alpha → диапазон и квантование → линейный цвет и кодирование вывода.
- **Стенд/переход:** Предыдущего снимка нет. Невизуальный CPU-снимок 01: массив 2×2 известных RGBA8, начало сверху слева; меняется один канал одного элемента. Alpha всегда 255, blending не подразумевается.
- **Объяснение/схема:** Рисунок сетки с адресом 4(y·width+x), каналами и цепочкой linear → sRGB → байты. Например, linear 0,5 кодируется примерно в 188, а не 128: кодирование не равно нормализации.
- **Код/границы:** Локальный `main.rs` читает массив и печатает координаты/значения; GPU-примера нет. Минимальный контракт: будущая sRGB-цель кодирует линейный выход автоматически; полная функция будет в 12.
- **Проверка:** Найти начало пикселя (1,1) → смещение 12 байт; изменить его R → остальные 15 байт неизменны. Объяснить, почему alpha=1 не включает прозрачность и почему монитор не служит точным измерителем чисел.

## 02. CPU, GPU и очередь

- **Вопрос/вход:** 01. Почему запись кадра не означает завершение рисования? Ресурс → логическое владение памятью CPU/GPU, включая UMA → команды → запись/submit/исполнение → очередь → presentation → явное ожидание завершения.
- **Стенд/переход:** Ссылка на неизменённый невизуальный снимок 01; массив и цветовые значения сохраняются. Теория 02 разбирает последовательность событий без нового проекта, окна, GPU-примера и графических регуляторов; изменяется место ожидания на временной схеме.
- **Объяснение/схема:** Две дорожки CPU/GPU и отдельная дорожка presentation: CPU записывает B, пока GPU выполняет A. Стрелки зависимостей показывают порядок, но длины полос не выдают выдуманную длительность.
- **Код/границы:** Нового executable нет, используется ссылка на `main.rs` из 01; схема описывает будущие ресурсы и команды без псевдовызовов неизвестного API. Не приравниваем submit к блокирующему ожиданию, present к завершению GPU, UMA к отсутствию правил доступа.
- **Проверка:** Расставить запись A, submit A, завершение A и допустимую работу CPU → запись предшествует submit, завершение следует исполнению, независимая работа CPU не обязана ждать. По одному submit нельзя вычислить время GPU.

## 03. Окно и очистка

Страницы 03a «Первый clear» и 03b «Жизненный цикл»: контрольная точка — один корректный кадр перед разбором восстановления; новых внешних prerequisites нет.

- **Вопрос/вход:** 02, цветовой контракт 01. События/redraw, логический/физический размер → instance/adapter/device/queue/surface → поддержка и запрос features/limits → format/usages/view → encoder/pass/attachment, clear/load/store → acquire/present/resize.
- **Стенд/переход:** От схемы 02 к снимкам 03a/03b: окно со сплошным linear-серым 0,5. Меняются только размер и запрос redraw; геометрии ещё нет. Present mode выбирается по поддержке с объяснением VSync, не как обещание задержки.
- **Объяснение/схема:** Автомат событий: ненулевой размер → configure → acquire → clear/store → submit → present; отдельные ветки пропуска и восстановления. Живой surface frame должен быть отпущен до повторной configure.
- **Код/границы:** Локальный `main.rs` содержит весь bootstrap, labels и диагностику validation. sRGB-формат выбирается явно; при отсутствии совместимого варианта — понятное завершение, не тихо неверный цвет. До обработчиков объясняются zero-size, устаревание/потеря surface и категории ошибок выбранной версии API.
- **Проверка:** Resize, минимизация и восстановление → нет configure нулевого размера, после восстановления снова серый кадр. Расчёт ожидаемого sRGB-кода даёт около 188; визуальная оценка не проверяет точность кодирования.

## 04. От трёх точек к треугольнику

- **Вопрос/вход:** 03. Как draw покрывает пиксели? Компоненты координат → WGSL scalar/vector/array, объявления, конструкторы, индексация, функции/return и области видимости → entry points/builtins → vertex_index → сборка примитива → vertex/fragment stages → pipeline.
- **Стенд/переход:** Снимок 03b → 04: тот же фон, размер, surface lifecycle; три явно заданные позиции и один линейный цвет. Координаты (-0,75;-0,75), (0,75;-0,75), (0;0,75), z=0,5, w=1; меняется одна позиция.
- **Объяснение/схема:** Рисунок «три вызова vertex → треугольник → покрытые выборки → fragment → attachment». Подписать clip-условия -w≤x,y≤w, 0≤z≤w и экранный Y вниз; при w=1 перевод прост, перспективы здесь нет.
- **Код/границы:** Добавляются локальный `shader.wgsl` и pipeline в `main.rs`; layout пустой, bindings отсутствуют. Явно выключаются culling, depth и blending; fragment — кандидат на вклад, не синоним пикселя.
- **Проверка:** Поменять две вершины местами → та же заполненная область при выключенном culling. Увести все x за 1 → треугольник исчезает; точные пограничные пиксели не фиксировать между GPU.

## 05. Граница оконной оболочки

- **Вопрос/вход:** 04. Что можно вынести, ничего не спрятав? Уже известный lifecycle → ответственность shell и примера → контракт вызовов → карта файлов → самостоятельный запускаемый снимок.
- **Стенд/переход:** Снимок 04 → 05 без изменения геометрии, shader, цвета, pipeline и настроек окна. Единственный эксперимент — перенос кода; знакомые resize и redraw проверяют сохранение поведения, а не новую графическую технику.
- **Объяснение/схема:** Диаграмма: пример передаёт известную из 03 конфигурацию device features/limits; shell управляет lifecycle/acquire/present и напрямую передаёт локальному примеру известные winit events, доступ к window и resize. Стрелки владения frame показывают безопасный момент configure.
- **Код/границы:** Из `main.rs` извлекается общая неизменяемая минимальная crate `shell`; локальны `sample.rs` и `shader.wgsl`. Снимки используют одну оболочку, не развивают её копии. Контракт включает только известную конфигурацию и raw forwarding, без input abstraction, камеры, таймеров, loaders, geometry helpers или renderer API.
- **Проверка:** Сопоставить запланированные кадры 04/05 и пройти resize/minimize/restore → тот же треугольник и фон. Для каждого вынесенного участка указать объяснение в 03/04; участок без такого происхождения не принимается.

## 06. Интерполяция

- **Вопрос/вход:** 04; переход через 05 сохраняет оболочку. Как получить плавный цвет внутри треугольника? Компонентные операции → смешивание на отрезке → три веса с суммой 1 → площади подтреугольников → барицентрические координаты → минимальная WGSL struct выхода → @location → flat для дискретного значения.
- **Стенд/переход:** Снимок 05 → 06: позиции и w=1 неизменны; сплошной цвет заменяется линейными RGB в вершинах. Compile-time константа shader выбирает градиент или постоянный цвет с пересборкой; подписи контрольных точек остаются на рисунке.
- **Объяснение/схема:** Треугольник с тремя цветными подплощадями и точкой P; отношение каждой площади к общей даёт вклад противоположной вершины. Равные веса в центроиде следуют из площадей, не из равноудалённости.
- **Код/границы:** `shader.wgsl`: объясняются поля, конструктор и доступ к struct для совместного возврата position/color; ресурсные структуры/layout остаются в 08. Режим задаётся константой, без uniform/bindings; `sample.rs`, оболочка и вывод sRGB прежние, матриц нет.
- **Проверка:** Вычислить цвет середины красно-зелёного ребра → linear (0,5;0,5;0); центроида → (1/3;1/3;1/3). Кадр должен согласоваться с градиентом, но центр пикселя может не совпасть с аналитической точкой.

## 07. Геометрия в буферах

Страницы 07a «Байты и vertex fetch» и 07b «Индексированная геометрия»: контрольная точка — прежний треугольник из Buffer; внешних prerequisites не добавляется.

- **Вопрос/вход:** 05, 06. Buffer/usages и upload → вершина как набор атрибутов → VertexFormat, offsets/stride, преобразование форматов → Rust ABI/bytemuck → index buffer → ranges и indexed vertex_index, first_vertex/base_vertex.
- **Стенд/переход:** Снимок 06 → 07a с прежними позициями/цветами; 07b явно заменяет треугольник прямоугольником из двух треугольников. Дальше сравниваются только indexed/nonindexed пути; координаты, цвета и настройки фиксированы.
- **Объяснение/схема:** Лента записи: position [f32;4] с offset 0, color [f32;4] с offset 16, stride 32; оба fetch-формата Float32x4. Стрелки шести индексов к четырём записям объясняют повторное использование; одинаковая позиция с другим цветом требует другой записи.
- **Код/границы:** `geometry.rs`, `sample.rs`, входы `shader.wgsl`; ABI проверяется явно. В 10 эти байты будут совместимы со storage без упаковки. Ненулевые смещения разбираются до упражнения; UV, нормалей и генератора мешей нет.
- **Проверка:** Посчитать четыре записи и шесть u16 → 128+12=140 байт против 192 байт шести записей. Оба пути дают одинаковое изображение; это размер полезных данных, не расход всей GPU-памяти и не доказательство ускорения.

## 08. Shader bindings и layout

Страницы 08a «Ресурс и привязка» и 08b «Смешанные поля»: контрольная точка 08a включает объяснение size/alignment статического vec4 до записи; 08b расширяет контракт без внешнего prerequisite.

- **Вопрос/вход:** 07. WGSL struct, module resource/address space/access → @location против @group/@binding → resource/view/range → bind group layout/group, pipeline layout/visibility → uniform → size/alignment/offset/array stride и uniform-ограничения → encase.
- **Стенд/переход:** Снимок 07b → 08a/08b: тот же индексированный прямоугольник и 32-байтовые вершины. В 08a статический tint=(1,1,1,1); в 08b добавляется gain=1. Меняется только цвет, без камеры и преобразований.
- **Объяснение/схема:** Путь CPU → байтовый диапазон → binding → shader. В 08a до upload: vec4<f32>, size=alignment=16, offset=0. В 08b до сериализации: Params с tint на 0, gain на 16, размером 32 при alignment 16. Отдельная таблица объясняет uniform-массивы и хвостовое выравнивание.
- **Код/границы:** Локальные `params.rs`, `sample.rs`, `shader.wgsl`; encase сериализует уже объяснённую структуру. Размер allocation, размер binding и требования layout не отождествляются; geometry и shell неизменны.
- **Проверка:** Сверить offsets 0/16 и размер 32 с CPU-расчётом; gain=0 → чёрная геометрия при прежнем фоне. Ошибку раскладки искать по байтам, не обещать, что validation обнаружит неверно сериализованный цвет.

## 09. Меняем данные во времени

- **Вопрос/вход:** 08. Какие значения увидит каждый draw? Время в секундах и скорость → write_buffer/staging → связь upload с submit → состояние команд против содержимого ресурса → отдельные bindings для разных draw.
- **Стенд/переход:** Снимок 08b → 09: прямоугольник и vertex/index buffers прежние; два draw рисуют по одному его треугольнику. Только gain меняется, фон и позиции фиксированы; локальные пауза/сброс используют уже известные события winit.
- **Объяснение/схема:** Timeline двух write_buffer и двух записанных draw перед одним submit: запись draw не фотографирует uniform. Рядом корректная схема с двумя отдельными uniform buffers/bind groups и загрузками перед submit.
- **Код/границы:** `sample.rs` вводит часы и два набора известных Params, `shader.wgsl` сохраняется. Gain=min(v·t,1), v в секунду; никаких sin, движения объектов, dynamic offsets или нового shell API.
- **Проверка:** При v=0,25 и t=2 ожидается gain=0,5; пауза сохраняет значение, сброс возвращает 0. Дать двум bindings gain=0,25/0,75 → половины различаются; одинаковые записи в один диапазон перед submit не обеспечивают отдельные значения каждому draw.

## 10. Read-only storage и vertex pulling

- **Вопрос/вход:** 08, 09 и indexed fetch из 07. Зачем читать storage в vertex shader? Storage binding/read-only → layout и limits → runtime-sized array и длина binding range → bounds → явная индексация → vertex pulling.
- **Стенд/переход:** Снимок 09 → 10: пауза, два прежних draw и Params, одинаковые индексы/позиции/цвета. Переключается только fetch/pulling; запись position vec4 + color vec4 остаётся 32-байтовой, buffer получает необходимые VERTEX/STORAGE usages.
- **Объяснение/схема:** Две дорожки от одних байтов: фиксированный fetch по offsets и storage-массив с array stride 32. Индексный буфер задаёт vertex_index и для pulling; вручную повторно читать индексы не нужно. Storage сам не преобразует VertexFormat.
- **Код/границы:** Локальные варианты `shader.wgsl`, layouts и выбор pipeline в `sample.rs`; без compute, компрессии и изменения ABI. До создания binding проверяются доступные storage limits/visibility, диапазон покрывает четыре записи; допустимые индексы гарантируются данными.
- **Проверка:** Для индексов 0,1,2,0,2,3 выписать адреса записей → 0,32,64,0,64,96. Пути должны дать одинаковый результат; некорректный индекс отклоняется учебной CPU-проверкой, без обещания конкретного кадра/validation error для OOB и без вывода о скорости.

## 11. Immediates и выбор механизма

- **Вопрос/вход:** 10. Как закрепить малый параметр за draw? Состояние команд → feature/limit → размер и layout immediate-блока → set_immediates → WGSL var<immediate> → действие на последующие операции.
- **Стенд/переход:** Снимок 10 → 11: прежние треугольники, доступ к вершинам и пауза. В отдельном read-only storage — два знакомых vec4 tint; uniform хранит общий gain, immediate u32 выбирает tint для каждого draw. Геометрия не перемещается.
- **Объяснение/схема:** Схема uniform gain + storage tint[2] + immediate index; timeline set(0)/draw/set(1)/draw противопоставлен upload из 09. Значение принадлежит состоянию команд, содержимое storage от этого не копируется.
- **Код/границы:** Локальная конфигурация из контракта 05 требует wgpu 30 Features::IMMEDIATES и достаточный max_immediate_size; pipeline задаёт immediate_size=4. Меняются `sample.rs` и shader, общая shell неизменна. Без поддержки запуск завершается с диагностикой; известный binding-путь 09 запускается отдельно, не через автоматический fallback. Механизм не объявляется native-only.
- **Проверка:** Индексы 0/1 дают выбранные цвета; удалить второй set → оба draw используют индекс 0. Проверить границу index<2 на CPU. Ни камера, ни обещание ускорения относительно uniforms в критерии не входят.

## 12. Цвет и его кодирование

- **Вопрос/вход:** 01, 06; снимок наследует 11. Почему среднее байтов не равно среднему света? Linear RGB → sRGB transfer function → UNORM отдельно от sRGB → decode/операции/encode → alpha и числовые данные вне sRGB-кодирования.
- **Стенд/переход:** Снимок 11 → 12: тот же прямоугольник, фиксированные draw и фон. Локальный режим сравнивает правильное и ошибочное смешивание чёрного/белого; для базового пути используются известные uniform bindings, поддержка immediates не обязательна.
- **Объяснение/схема:** График кусочной transfer function с точкой linear 0,5 → sRGB≈0,735; две цепочки смешивания показывают, где ошибочно усредняются коды. Финальная sRGB-цель выполняет encode ровно один раз, как уже в 03.
- **Код/границы:** Локальный CPU-расчёт в `color.rs` и диагностический `shader.wgsl`; геометрия/shell прежние. Для сравнения ошибочное среднее кода декодируется перед правильной целью; текстур, HDR и blending ещё нет.
- **Проверка:** Правильное среднее даёт код около 188, среднее кодов — 128, то есть linear≈0,216. Для кода 128 UNORM≈0,502, но sRGB decode≈0,216; различать расчёт и субъективную яркость дисплея.

## 13. Текстуры и sampling

Страницы 13a «Тексели и upload» и 13b «UV и фильтр»: контрольная точка — textureLoad известного массива; sampling не требует нового внешнего prerequisite.

- **Вопрос/вход:** 08, 12. Тексель/пиксель → Texture/View/format/usages → upload/row layout → UV и центры → интерполяция UV → sampler/address modes → nearest/билинейные веса → textureLoad против textureSample.
- **Стенд/переход:** Снимок 12 → 13a/13b: прямоугольник, координаты и вывод прежние; вместо аналитического цвета — асимметричный массив 2×2 RGBA8 sRGB. По очереди меняются фильтр и address mode; цветовые множители сбрасываются в 1.
- **Объяснение/схема:** Рисунок четырёх текселей с центрами UV 0,25/0,75 и четырьмя весами выборки. Декодирование цвета предшествует смешиванию; linear-фильтр не является названием цветового пространства. Отдельная схема рядов объясняет upload.
- **Код/границы:** Локальные `texture.rs`, `sample.rs`, shader; UV добавляется отдельным vertex buffer, базовая запись 32 байта сохраняется, используется fetch. Очередной upload не получает без объяснения ограничения encoder-copy; view требует совместимого формата. Файловый загрузчик и runtime-подписи не нужны.
- **Проверка:** В центрах nearest воспроизводит четыре известных цвета; в (0,5;0,5) bilinear даёт среднее четырёх linear RGB. textureLoad выбирает целый тексель без sampler; clamp/repeat за UV=1 дают предсказанную адресацию, не произвольный новый цвет.

## 14. Уменьшение и mipmaps

- **Вопрос/вход:** 13, время/upload из 09. Почему уменьшение чувствительно к фазе? Дискретизация/footprint → aliasing → предварительная фильтрация → mip-уровни → изменение UV между пикселями → LOD, его ограничение и смешивание уровней; allocation не создаёт содержимое.
- **Стенд/переход:** Снимок 13b → 14: прежний прямоугольник, шахматка 8×8, repeat. Фиксируем viewport и k для footprint≈2 текселя/пиксель. UV·k+(phase,0), phase=t/8 за 0–2 секунды; пауза/сброс из 09. Сравниваем одинаковый проход с nearest внутри уровня, LOD clamp 0 против 1.
- **Объяснение/схема:** Пирамида 8→4→2→1, footprint и последовательность фаз 0, 1/16, 1/8, 3/16, 1/4. При footprint≈2 ориентир LOD≈1; предфильтрация уменьшает зависимость от положения выборки, не восстанавливает детали.
- **Код/границы:** `texture.rs`: CPU box 2×2, decode → среднее linear → encode RGB; alpha=1, загрузка каждого уровня. Локальные shader/Params получают k/phase; shell неизменна. Без камеры/RTT/compute; размеры степеней двойки.
- **Проверка:** 85 текселей → 340 RGBA8-байт; среднее linear 0,5 → mip RGBA=(188,188,188,255). Сравнить внутренние пиксели на указанных фазах → меньшая фазовая чувствительность mip-пути. Кадр без mips тоже может выглядеть серым; общая смена чёрного/белого не гарантируется, геометрические края не проверяются.
