# Ответвления B1–B8 и B10–B12: паспорта этапа 2

Общие правила: [введение в паспорта](../CHAPTER_PASSPORTS.md). Основание: [план](../REWRITE_PLAN.md), [карта знаний](../KNOWLEDGE_MAP.md). Проект будущих глав; B9 исключён.

Входы непосредственные, зависимости наследуются. «Основа» обязательна внутри ветки. Снимки самостоятельные, стенды фиксированные; фреймворк заморожен.

## B1a. Измеряем исполнение

- **Вопрос/вход:** где расходуется время одинаковой обработки изображения? Вход: 03, 09, 30. Различаем подготовку CPU, запись/submit, исполнение GPU и ожидание показа; длительность submit не выдаём за длительность шейдера.
- **Стенд/переход:** fragment/compute варианты 30; добавляем прогрев, фиксированное число кадров и отключаемую диагностику, сохраняя размеры/формат.
- **Объяснение/схема:** временная ось query → resolve → copy → completion → map; разность timestamps умножаем на период, получая наносекунды. Показываем задержку чтения, влияние VSync и разброс выборки.
- **Код/границы:** основа: CPU-замеры и GPU timestamps только при поддержке нужных features; отложенное чтение без ожидания каждого кадра. Без поддержки явно выводим «GPU-время недоступно», не подставляем CPU-время.
- **Проверка:** изменить разрешение → отчёт содержит оба размера, backend/GPU, прогрев, медиану и разброс; изображения совпадают с допуском. Ускорение заранее не предписывается.

## B1b. Возможности и диагностика

- **Вопрос/вход:** как отличить ошибку программы от недоступной возможности устройства? Вход: B1a, 11. Разделяем capabilities адаптера, запрос устройства и требования конкретного пути исполнения.
- **Стенд/переход:** тот же эксперимент; добавляем диагностику и принудительное отключение необязательного пути.
- **Объяснение/схема:** «операция → feature/limit → запрос → проверка → допустимый путь». Capture показывает проходы/ресурсы, не заменяя замер; labels связывают capture с текстом.
- **Код/границы:** основа: отчёт реально используемых limits/features, содержательные labels и обработка validation. Инструкция одного native capture с указанием backend и инструмента; не объявляем capture или immediates исключительно native-возможностями. Другие расширения остаются упражнениями.
- **Проверка:** принудительно отключить timestamps → работающий кадр и явная причина отсутствия метрики; неверный binding в отдельном диагностическом режиме → ошибка с узнаваемым label, а не молчаливый чёрный экран.

## B2a. Экземпляры общей геометрии

- **Вопрос/вход:** как рисовать много объектов одного mesh? Вход: 07, 10, 28. Instancing не меняет материал автоматически.
- **Стенд/переход:** известные плоскости 28 с разными переносами/цветами: отдельные draw заменяем instanced draw. Геометрию сохраняем без нового генератора.
- **Объяснение/схема:** две оси адресации: vertex_index выбирает вершину, instance_index объект. Показываем instance step mode и storage-таблицу как альтернативы доставки одинаковых данных; ненулевой first_instance смещает индекс экземпляра.
- **Код/границы:** основа: оба способа per-instance чтения, отдельный/объединённый draw. Разные pipelines не объединяем. Замеры требуют B1a.
- **Проверка:** нарисовать диапазон экземпляров 3..7 → четыре плоскости с цветами записей 3–6; переключение доступа сохраняет их положения/цвета.

## B2b. Диапазоны параметров объектов

- **Вопрос/вход:** когда удобны dynamic offsets, а когда таблица storage? Вход: B2a, B1a, 08, 09. Сравниваем размещение параметров отдельно от batching.
- **Стенд/переход:** отдельные draw прежних плоскостей: storage с индексом заменяем uniform с dynamic offset.
- **Объяснение/схема:** выводим шаг записи как округление размера вверх до min_uniform_buffer_offset_alignment. Рисуем payload, padding, binding range и offset; allocation size не равен размеру доступной шейдеру записи.
- **Код/границы:** основа: один буфер, явный ABI/offsets, загрузка до submit. Раздельно считаем payload, padding, команды; без allocator/renderer.
- **Проверка:** выбрать вторую и последнюю записи → правильные цвета без validation errors; вычисленный последний диапазон укладывается в allocation. Замеры при равном количестве draw фиксируют наблюдение, не универсального победителя.

## B3a. Представление без дублирования

- **Вопрос/вход:** какие данные различаются между повторяющимися объектами? Вход: 10, 28, B1a. Стенд выбираем независимо от игровых форматов.
- **Стенд/переход:** выбираем простой знак из двух пересекающихся треугольников с фиксированной ориентацией. Сравниваем развёрнутые вершины каждого знака и общий шаблон плюс перенос, равномерный масштаб и цвет объекта.
- **Объяснение/схема:** делением и остатком получаем object/vertex; восстанавливаем p = center + scale * template. Сопоставляем удалённые данные и добавленные вычисления.
- **Код/границы:** основа: оба представления читаются через storage, одинаковые draw и изображение; сначала везде f32. Никаких обязательных компактных квадов, квантизации вращений или генератора сложной геометрии.
- **Проверка:** удвоить число знаков → таблица байтов следует формулам N*V*vertex_stride и V*template_stride + N*object_stride; изображения совпадают. Upload и GPU-время учитываются отдельно от числа записей.

## B3b. Упаковка и погрешность

- **Вопрос/вход:** сколько точности обменять на меньшую запись? Вход: B3a, 12. Меняем только числовое кодирование.
- **Стенд/переход:** те же знаки в ограниченном объёме; перенос по каждой оси кодируем 16 битами, линейный цвет четырьмя 8-битными каналами, масштаб оставляем f32.
- **Объяснение/схема:** q = round((x-a)*65535/(b-a)); восстановление обращает отображение. При отсутствии clipping ошибка оси не больше (b-a)/(2*65535), пространственная ошибка ограничена корнем суммы квадратов осевых границ. Биты, маски и сдвиги выводим на двух упакованных значениях.
- **Код/границы:** основа: CPU pack/WGSL unpack, явный stride с padding; выход за объём отвергается, не насыщается скрыто. Цветовая ошибка канала до 1/510; вращение не квантуем.
- **Проверка:** крайние и средние координаты → ошибки внутри границы; увеличенный диагностический масштаб показывает смещение. Отдельно сравниваем bytes/upload/время, не обещая выигрыша от добавленной ALU.

## B4. Нормаль из текстуры

- **Вопрос/вход:** как направление в normal map становится мировой нормалью? Вход: 13, 22, 24, 25. UV-конвенция стенда: рост U вдоль local +X, рост V вдоль +Y, геометрическая нормаль +Z.
- **Стенд/переход:** размеченная плоскость с разными участками наклона к +T и +B, не симметричный шум. Свет последовательно ставим к +X и +Y; затем вращаем и неравномерно масштабируем плоскость.
- **Объяснение/схема:** решаем две связи рёбер с UV-разностями для T/B; объясняем вырожденный UV, handedness и зеркальность. N преобразуем inverse-transpose, T обычной линейной матрицей, ортогонализуем; B восстанавливаем с учётом ориентации преобразования.
- **Код/границы:** основа: linear normal texture, decode 2c-1, нормализация, явный знак зелёного канала и TBN; общего tangent-generator пока нет.
- **Проверка:** нейтральная карта → прежний свет; наклон +T ярче при свете +X, +B при +Y. Зеркальный UV и преобразование сохраняют предсказуемое мировое направление.

## B5a. Соседи и ping-pong

- **Вопрос/вход:** как читать соседей одного поколения? Вход: 29, 30. Независимые выходные записи не разрешают обновлять общий вход на месте.
- **Стенд/переход:** единичный импульс в R, формат RGBA8Unorm из 30; вводим усреднение трёх горизонтальных текселей и повторяем шаг.
- **Объяснение/схема:** A читается, B записывается; следующий dispatch меняет роли. На границах clamp; схема поколений показывает распространение импульса.
- **Код/границы:** основа: разные input/output textures, textureLoad, bounds check, два законных набора привязок. Между dispatch зависимость обеспечивается порядком команд и моделью доступа wgpu, не workgroupBarrier. Fragment-вариант сохраняем для сравнения; измерения требуют B1a.
- **Проверка:** CPU-эталон квантует UNORM после каждого прохода. Вдали от края шаг 1 → три 85/255; шаг 2: идеальные [1,2,3,2,1]/9, сохранённые [28,57,85,57,28]/255. Диагностическая разность GPU/эталона нулевая; точное сохранение суммы при дальнейшей квантизации не гарантируется.

## B5b. Общая память группы

- **Вопрос/вход:** как переиспользовать чтения внутри workgroup? Вход: B5a. Фильтр неизменен.
- **Стенд/переход:** тот же импульс и горизонтальный фильтр; группа загружает плитку с двумя крайними дополнительными значениями, затем вычисляет свои выходы.
- **Объяснение/схема:** рисуем соответствие global/local индексов и halo. Барьер разделяет загрузку и чтение общей памяти только внутри группы; разные группы не получают глобальной точки встречи. Storage barrier также не синхронизирует все группы dispatch.
- **Код/границы:** основа: workgroup array, согласованная загрузка, один равномерно достигаемый барьер. Лишние invocations участвуют в загрузке и барьере; bounds ограничивает выходную запись после него. Размер плитки проверяется по limits; раннего return перед барьером нет.
- **Проверка:** ширина изображения на единицу больше размера группы → результат совпадает с B5a, включая границу групп и последний пиксель. Меньшее число загрузок не объявляется ускорением без B1a.

## B5c. Атомарный отбор

- **Вопрос/вход:** как invocations получают разные места в списке? Вход: 29, B1a для readback/CPU-проверок. Workgroup memory и scan не нужны.
- **Стенд/переход:** независимые записи 29 заменяем добавлением чётных ID в ограниченный список.
- **Объяснение/схема:** atomicAdd возвращает предыдущее значение счётчика, то есть уникальный билет. Порядок билетов недетерминирован; атомарность одного счётчика не публикует законченный список всем invocations текущего dispatch.
- **Код/границы:** основа: сброс счётчиков до запуска, запись только при ticket < capacity, отдельный overflow flag. Число входов ограничено диапазоном u32; следующий dispatch читает min(count, capacity). При переполнении сохраняется произвольное допустимое подмножество, приложение явно сообщает потерю.
- **Проверка:** ID 0..9, capacity 5 → множество {0,2,4,6,8}; capacity 3 → три различных чётных ID, count=5 и overflow=1. Порядок не проверяем.

## B5d. Сведение массива

- **Вопрос/вход:** как свести массив к сумме? Вход: B5b, B1a для readback/CPU-проверок. Float atomics не требуются.
- **Стенд/переход:** массив неотрицательных целых вместо изображения; группы выдают частичные суммы, затем сводим их.
- **Объяснение/схема:** парное сложение сокращает число активных элементов вдвое; рисуем дерево для восьми чисел. Вне входного диапазона подставляем нейтральный ноль; между уровнями все invocations проходят барьер, даже переставшие складывать.
- **Код/границы:** основа: размер группы степенью двойки, workgroup reduction и несколько dispatch до одного результата. CPU задаёт размеры запусков, не читает промежуточные суммы. Ограничиваем данные так, чтобы u32 не переполнялся; float и его неассоциативность только дополнительное упражнение.
- **Проверка:** массив 1..10 → 55; пустой → заранее записанный ноль; размер на единицу больше группы → сумма совпадает с CPU, включая последний неполный блок.

## B5e. Scan и стабильное уплотнение

- **Вопрос/вход:** как сохранить порядок отобранных элементов? Вход: B5d; readback/CPU-проверки наследуют B1a. B5c не prerequisite реализации.
- **Стенд/переход:** массив ID и флаги; вместо общей суммы вычисляем будущие позиции элементов.
- **Объяснение/схема:** exclusive prefix sum считает единицы строго слева. Выводим удвоение расстояния сложения на двух чередующихся массивах общей памяти; затем сканируем суммы блоков и прибавляем блоковые offsets. Inclusive результат переводим в exclusive вычитанием собственного флага.
- **Код/границы:** основа: многоуровневый scan отдельными dispatch, scatter, равномерные барьеры. Ёмкость равна числу входов: переполнение невозможно. Оптимизация дерева необязательна.
- **Проверка:** [1,0,1,1,0] → offsets [0,1,1,2,3], итоговые ID [0,2,3]. Повторить через границу блоков и с пустым входом → тот же стабильный порядок и корректный count.

## B6a. Bloom до вывода

- **Вопрос/вход:** как распространить яркость на соседние пиксели? Вход: B5a, 33. B5b–B5e не требуются.
- **Стенд/переход:** контрастная HDR-сцена 33; добавляем bright extraction, горизонтальный и вертикальный фильтры, сложение с исходным HDR перед exposure/tone mapping.
- **Объяснение/схема:** определяем порог в линейных единицах сцены. Нормированные одномерные веса дают двумерное ядро произведением; поэтому два прохода воспроизводят выбранный separable фильтр. Смещения измеряем в текселях входа, а не выхода.
- **Код/границы:** основа: фиксированный blur без mip-пирамиды, clamp на границах, отдельные targets и просмотр каждого. Понижение разрешения оставляем упражнением с явной сменой масштаба фильтра; bloom является художественной аппроксимацией, не физической моделью оптики.
- **Проверка:** константное выделенное поле → фильтр сохраняет значение; одиночная яркая точка → симметричное пятно. Выключение bloom точно возвращает путь 33; tone mapping применяется только после композиции.

## B6b. Частицы с постоянными слотами

- **Вопрос/вход:** как обновлять движение на GPU и рисовать состояние без readback? Вход: 29, B2a, 27. Соседних взаимодействий нет, поэтому вся B5 не нужна.
- **Стенд/переход:** фиксированный пул, пауза и одиночный шаг; добавляем движение и respawn из явной таблицы начальных состояний, без PRNG.
- **Объяснение/схема:** скорость в м/с, ускорение в м/с²; выводим v'=v+a*dt, p'=p+v'*dt. Billboard использует right/up камеры. Lifetime кратен timestep; по истечении шага слот восстанавливает свою исходную запись, без случайного helper.
- **Код/границы:** основа: фиксированный timestep с ограничением накопления, независимое обновление каждого слота и instanced billboards. Additive blending с depth test без depth writes устраняет потребность сортировки именно для этого эффекта; уплотнение по B5e необязательно.
- **Проверка:** нулевое ускорение, скорость 2 м/с → за 60 шагов по 1/60 с смещение 2 м с float-допуском; reset повторяет состояние. Обычную alpha-прозрачность корректной без сортировки не обещаем.

## B7a. GPU-driven видимость

- **Вопрос/вход:** как GPU выбирает объекты и задаёт число экземпляров? Вход: 28, B2a, B5c, B1a, 19. Render graph и стабильный scan не обязательны.
- **Стенд/переход:** непрозрачные экземпляры одного mesh: CPU-отбор заменяем GPU-списком и indexed indirect draw; тест неизменен.
- **Объяснение/схема:** из clip-неравенств выводим мировые плоскости frustum; сфера снаружи, если знаковое расстояние меньше -radius. Консервативные сферы получают максимальный масштаб объекта. Далее схема reset → cull/append → finalize arguments → draw.
- **Код/границы:** основа: layout indirect arguments, STORAGE/INDIRECT usages, проверка limits, first_instance=0. Список вмещает все объекты; если диагностически уменьшен, overflow переводит finalize на рисование всех через исходную таблицу, не скрывает объекты. Multi-draw и occlusion culling вне реализации.
- **Проверка:** все снаружи → instance_count=0; пересечение сферы с плоскостью → объект сохранён; переполнение → полный корректный кадр без culling. Сверка множества с CPU и замеры не предполагают ускорения.

## B7b. Локальный граф кадра

- **Вопрос/вход:** что автоматизировать в кадре? Вход: 30, B6a. B7a, scan, PBR не требуются.
- **Стенд/переход:** bloom-кадр B6a переводим в граф. Вместо исходного ping-pong выделяем отдельные textures версиям; сравниваем результат, не скорость при изменившихся allocations.
- **Объяснение/схема:** версия имеет одного writer; каждое чтение, включая attachment Load, зависит от производителя. Топологический порядок выводим удалением узлов без предшественников; остаток означает цикл. Отмечаем всех readers и lifetime.
- **Код/границы:** основа: отдельная physical texture каждой живой версии, без aliasing. Для Load копируем предыдущую версию в новый attachment перед проходом. Проверяем producers/циклы, пересоздаём targets при resize. Оболочку не меняем; async compute не обещаем.
- **Проверка:** две ветви читают старую версию перед её логической заменой → обе получают исходные данные. Перестановка объявлений сохраняет кадр благодаря независимому backing и полному writer/read-графу; цикл → ошибка до submit.

## B8a. Загрузка сцены

- **Вопрос/вход:** как загрузить данные 28? Вход: 22, 28, 24. Сохраняем знакомое освещение, ограничивая поддерживаемые материалы.
- **Стенд/переход:** два узла, общий mesh; ручное создание заменяем загрузкой, сохраняя transforms/цвета.
- **Объяснение/схема:** формат задаёт массивы атрибутов, индексы, локальные матрицы, ссылки на материалы и иерархию. World дочернего узла получается произведением world родителя и local; проверяем диапазоны, циклы, UV и normal matrix до GPU-upload.
- **Код/границы:** основа: узкий собственный входной формат, статические треугольники без skinning/анимации. glTF-адаптер необязателен и требует объяснения accessors, stride, типов и координат; PBR-параметры не подменяем Blinn–Phong молча. Ассеты сопровождаем лицензией/атрибуцией; текущие файлы не обещаются готовыми.
- **Проверка:** два узла → две позиции, одна геометрия; неверный индекс → ошибка до upload. Поворот родителя даёт рассчитанное положение ребёнка.

## B8b1. Угловая мера и BRDF

- **Вопрос/вход:** что измеряют свет и отражение? Вход: 25, 33. До PBR вводим угловую меру, radiometry и нормировку BRDF.
- **Стенд/переход:** известная плоскость 25, числовые таблицы направлений; заменяем эмпирический diffuse нормированным Lambert, без новой геометрии.
- **Объяснение/схема:** solid angle: площадь единичной сферы, ср; из полос выводим dω=sin(theta)dtheta*dphi. Взвешенные суммы переходят в интеграл. Radiance Li: Вт/(м²·ср); irradiance E=∫Li cos(theta)dω: Вт/м². BRDF f=dLo/dE: 1/ср; Lo=∫fLi cos(theta)dω. Проекция полусферы даёт ∫cos(theta)dω=pi, поэтому Lambert f=albedo/pi.
- **Код/границы:** основа: CPU-суммы и direct Lambert. Directional intensity задаём как irradiance Eperp на перпендикулярной лучам площадке; Lo=f*Eperp*max(N·L,0), без фиктивного телесного угла точечного направления.
- **Проверка:** веса сферы → 4*pi, косинусные веса полусферы → pi при сгущении сетки; albedo=0.5, Eperp=pi, N=L → Lo=0.5; наклон 60° → 0.25.

## B8b2. Прямой микрофасетный PBR

- **Вопрос/вход:** как микрограни формируют блик? Вход: B8b1. Загрузчик и normal mapping не нужны.
- **Стенд/переход:** плоскость 25, перспективная камера: V меняется по поверхности, давая пространственный блик. Directional light с Eperp из B8b1; roughness/metallic варьируем раздельно, без сферы/генератора.
- **Объяснение/схема:** выводим GGX D через распределение проецируемой площади: ∫D(H)(N·H)dω=1, не ∫D dω=1. Через half-vector объясняем Smith G, Schlick F и знаменатель микрофасетного отражения; каждому даём формулу и численный пример до WGSL.
- **Код/границы:** основа: F0=mix(0.04,baseColor,metallic); f=(1-metallic)*(1-F)*baseColor/pi+DGF/(4(N·L)(N·V)). Цвет линейный; alpha=max(roughness²,0.001). При N·L≤0 или N·V≤0 возвращаем ноль, защищаем нормализацию L+V и знаменатели. Lo=f*Eperp*max(N·L,0); многократное рассеяние исключено.
- **Проверка:** metallic=0 → F0=0.04; metallic=1 → F0=baseColor, diffuse=0. Скользящие углы дают конечные неотрицательные значения; roughness расширяет блик. Точную компенсацию потерянной энергии не обещаем.

## B8c. Окружение и интеграл света

- **Вопрос/вход:** как применить интеграл к карте окружения? Вход: B8b2, 13, 17. Угловая мера и BRDF уже введены в B8b1.
- **Стенд/переход:** постоянное окружение, яркий сектор, асимметричная разметка направлений; добавляем diffuse irradiance.
- **Объяснение/схема:** для latitude-longitude выводим вес текселя Δphi*(cos(theta0)-cos(theta1)) из полос B8b1. Суммируем Li*cos(theta)*вес для irradiance; учитываем шов, полюса и ориентацию карты. Равные UV-площади не означают равные телесные углы.
- **Код/границы:** основа: явная CPU-квадратура маленькой карты и diffuse IBL, без случайных выборок и скрытого convolution helper. HDR-файл окружения необязателен; цветовые данные линейные.
- **Проверка:** сумма весов полной сферы → 4*pi; постоянное Li=1 → irradiance≈pi и Lambert Lo≈albedo. Поворот яркого сектора предсказуемо меняет освещённую сторону.

## B8d. Выборки для specular IBL

- **Вопрос/вход:** как оценивать интеграл без обхода всей карты для каждого пикселя? Вход: B8c. B8a нужен только для упражнения с моделью, B4 только для normal maps.
- **Стенд/переход:** сравниваем квадратуру и выборочную оценку прежнего окружения/BRDF; добавляем specular IBL.
- **Объяснение/схема:** вероятность, плотность p на стерадиан и среднее дают sum(fLi cos/p)/N. Из B8b2 получаем p(H)=D(H)*max(N·H,0), выводим выборку через накопленную вероятность и якобиан p(L)=p(H)/(4|V·H|). Отклонённые направления дают нулевой вклад в исходные N; seed/генератор объясняем до применения.
- **Код/границы:** основа: небольшой детерминированный reference-render с прямой Monte Carlo оценкой и явным LOD=0, без претензии на realtime. Prefiltered environment, split-sum LUT и их дополнительная аппроксимация остаются отдельным необязательным продолжением, не необъяснённым helper.
- **Проверка:** постоянное окружение и несколько roughness → средняя оценка согласуется с квадратурой при росте N; фиксируем абсолютную ошибку и разброс по seeds, не требуем монотонности каждого запуска. Финальный цвет проходит HDR-вывод 33 один раз.

## B10. Кубические карты и skybox

- **Вопрос/вход:** как текстурировать направления, а не точки поверхности? Вход: 13, 19, 20, 22. Фон и окружение не имеют поверхностей.
- **Стенд/переход:** куб над полом со статической камерой; добавляем асимметрично размеченное окружение (градиент по высоте и метка у +X), сцену не меняем.
- **Объяснение/схема:** кубическая текстура — шесть граней одного mip-уровня; направление выбирает грань по максимальной по модулю компоненте и тексель внутри неё. Направление на пиксель неба выводим из вершин куба, переносимого в позицию камеры: перенос не меняет направление.
- **Код/границы:** основа: view с `TextureViewDimension::Cube`, upload шести граней, отдельный pipeline с z = 1 и compare GreaterEqual без записи depth, рисуем последним. Выборка в фрагменте по интерполированному направлению; irradiance и отражения — B8, не здесь.
- **Проверка:** направление (1, 0, 0) даёт тексели метки +X на соответствующей стороне; вращение камеры сохраняет согласованность фона; выключение неба не меняет сцену.

## B11. Тени точечного источника

- **Вопрос/вход:** как получить карту глубины во все стороны от точки? Вход: 26, 31. Направленный свет стенда заменяется точечным внутри сцены.
- **Стенд/переход:** куб и пол из 31, источник над кубом; предсказания 31a/b сохраняются для каждой стороны.
- **Объяснение/схема:** шесть перспективных проходов 90°×90° с общими near/far в кубическую depth (или атлас 2×3); грань выбирает направление из источника к фрагменту, эталонная глубина — расстояние; bias и PCF наследуем из 31b, отдельно обсуждая разницу погрешностей по граням.
- **Код/границы:** основа: depth-only проходы на грань без дублирования геометрии, comparison-выборка по направлению, ограничение дальности источника задаёт far; за пределами дальности фрагмент не затеняется, как в 26.
- **Проверка:** объект между источником и полом отбрасывает тень во все стороны; независимое отключение граней показывает их покрытие; численная сверка видимости фиксированных точек пола.

## B12. Ambient occlusion

- **Вопрос/вход:** откуда затенение в углах и щели, куда прямой свет не попадает? Вход: 19, 24, 30. Локальная модель освещения не знает соседних поверхностей.
- **Стенд/переход:** куб в углу над полом; между освещением и выводом добавляем проход затенения.
- **Объяснение/схема:** позиция фрагмента восстанавливается из нелинейной depth обратной проекцией; полусфера выборок вокруг интерполированной нормали с поворотом по касательной; окклюзия — по разности глубостей с range check; затем blur и умножение ambient-вклада до сложения источников.
- **Код/границы:** основа: fullscreen-проход по depth и нормалям, отдельный blur, композиция; фиксированный набор выборок с поворотами, без temporal accumulation и denoise. Эталон фиксированных точек — CPU-трассировка той же геометрии.
- **Проверка:** точка в углу темнее центра пола; пустая сцена даёт единицу; плоская стена — константа при поворотах выборок; A/B с CPU-эталоном в допуске.

## Вне охвата

Поддерживается API, но учебных глав не планируется (пересмотреть при спросе):

- stencil-тесты: зеркала, контуры; parallax mapping — возможное упражнение после B4;
- кватернионы, picking, скелетная анимация, рельефы;
- отрисовка текста.

Невозможно в переносимом ядре WebGPU; native-расширения wgpu существуют, но остаются вне маршрута:

- geometry-шейдеры, тесселяция, mesh-шейдеры, трассировка лучей.
